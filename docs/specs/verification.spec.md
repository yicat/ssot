# 核验：凭什么认为它对（底座）

## 目的

系统中的内容来自非权威渠道（社区攻略、玩家实测、二手转载）。
它们**不能因为「被采集进来」就被当作事实使用**。

本规格是**底座**，定义：什么算核验、谁能核验、核验到什么程度、未核验的内容如何使用。

核心立场两条：

1. **系统不能让内容「看起来已经核验过」。** 默认一切未核验；
   未核验内容**允许使用，但必须可见**。
2. **没有独立的核验界面与队列。** 上一版把人固定成流程里的一环——给一个长列表让他逐条看。
   这个结构里人负责提要求与拍板，交叉校验是主对话 Agent 的活。
   核验**记录**仍然保留（谁、何时、凭什么、验到哪一部分），只是不再排队。

**核验与拍板是两件事，不能合并：**

| | 核验 | 拍板（见 `agent.spec.md`） |
|---|---|---|
| 回答 | 凭什么认为它对 | 这个改动可以进事实源了吗 |
| 谁做 | 人与 agent 均可提出，**批准必须是人** | 只能是人 |
| 产物 | 一条核验记录 | 一次生效 |
| 是否排队 | **不排队**：按需追加 | 排在待办区的「待拍板」 |

## 术语

- **依据（evidence）**：支持某个说法的东西——实测样本、官方文案、统计数据、可重算的推导。
  **依据 ≠ 来源**：来源是「谁说的」，依据是「凭什么这么说」。
- **核验（verification）**：对可信度做出的、**有记录的判断**。
- **核验方法**：得出该判断的手段，分四级（见下）。方法不同，可信度不同。
- **独立来源**：彼此不存在引用、转载或同源关系的来源。
  **不独立的多个来源不是多个证据。**
- **部分核验**：只核验了某一部分（例如依据可信但结论未验证）。
- **争议（disputed）**：两条或多条说法互相冲突且尚未裁决。
- **未核验比例**：一个输出所依赖的内容中，没有核验记录的比例。

## 核验方法分级（强度从高到低）

| 级别 | 方法 | 含义 | 必须同时记录 |
|---|---|---|---|
| 1 | **实测** | 在实际环境观测 | 版本、配置、样本数、是否可复现 |
| 2 | **重算** | 由其他已核验内容推导且结果一致 | 推导链 |
| 3 | **多源** | 多个**独立**来源一致 | 各来源及其独立性判定结果 |
| 4 | **编审** | 人工阅读后判断接受 | 核验人、理由 |

**四级不得互相等同。** 尤其是「编审」——它是人工判断，不是验证。

## 领域规则（Given-When-Then）

### 默认未核验

- Given 任何外部内容被导入 When 入库 Then 其核验状态为「未核验」，
  **不得默认视为已核验**
- Given 自动检查（格式、引用完整性、可否重算、是否与已有内容冲突）通过 When 记录 Then
  状态为「已自动预检」，**不得等同于已核验**
- Given 一条未核验内容 When 被答案引用 Then 输出必须**显式标注**
- Given 一个输出 When 给出 Then 必须包含它依赖内容的**未核验比例**（见 `case.spec.md`）

### 核验的生效

- Given agent 完成一次交叉校验 When 得出「一致 / 矛盾 / 单源」的结论 Then
  它是一条**提议**（见 `agent.spec.md`），**不直接改变**任何内容的可信度判断
- Given 一条核验记录 When 生效 Then 必须有人拍板，且记录批准者与理由；
  **批准者必须是是人**
- Given 一条核验记录 When 记录 Then 必须能回答四件事：
  **谁、何时、凭什么、核验到哪一部分**——缺任一项即拒绝
- Given 核验记录只有状态而没有理由 When 记录 Then **拒绝**——
  无追责的核验等于没有核验
- Given 提出者与批准者 When 记录 Then **分别标识**，不得只记一个
- Given 核验记录 When 记录 Then **不进入任何队列**：
  它是按需追加的，不存在「等人核验的清单」

### 核验方法的记录要求

- Given 一条内容以「实测」记录核验 When 缺少版本、配置或样本数 Then
  **拒绝**该核验记录
- Given 实测样本数为一 When 记录 Then 允许但标记「**单样本**」，
  其可信度低于多样本
- Given 一条内容以「重算」记录核验 When 推导链上存在未核验内容 Then
  记为该链的最低可信度，**不得高于其依赖**
- Given 仅有单一来源 When 人工接受 Then 方法必须记为「编审」，
  可信度**不得等同于**实测或多源
- Given 方法为「多源」 When 记录 Then 必须给出各来源的**独立性判定结果**；
  未给判定结果的，视为「编审」

### 独立性判定

- Given 来源 A 引用了来源 B When 判定独立性 Then 二者**不独立**，合并为一个证据
  （转载关系见 `document.spec.md`）
- Given 两个来源的文本高度雷同 When 判定独立性 Then 标记为「**可能同源**」，
  不作为独立证据
- Given 多个来源发布时间相近且内容雷同 When 判定 Then 标记为可疑，转人工确认
- Given 判定为不独立的多个来源 When 记录核验 Then 证据数计为一
- Given 交叉校验 When 跑 Then 独立来源只有一份时结论只能是「单源」，
  **不得**呈现为「多源一致」

### 部分核验

- Given 一条内容的依据可核验而其结论不可核验 When 核验 Then
  允许记录「依据已核验、结论未核验」
- Given 一条内容带多个限定条件而只核验了其中一部分 When 核验 Then
  未覆盖的条件仍标记为未核验
- Given 一条内容包含主观判断（例如「某式神在此活动中很强」） When 核验 Then
  **只核验依据是否充分，不声称结论已被验证**

### 争议

- Given 两条说法冲突 When 遇到 Then 二者**均**标记为「有争议」，
  **不得自动择一**
- Given 争议 When 需要裁决 Then 走歧义的登记与裁决（见 `decision.spec.md`），
  裁决记录含依据、裁决者、时间
- Given 分歧无法裁决 When 处理 Then 保留争议状态，**不得强行给出结论**
- Given 一条内容被驳回 When 记录 Then 它**不得出现在任何输出中**，
  但条目保留（驳回是审计轨迹）

### 变更触发

- Given 来源内容的修订标识发生变化 When 检测到 Then
  由该来源产出的内容全部标为「**依据已变**」（不再叫「待重核验」——
  没有队列可排，标注才是能起作用的东西）
- Given 一条内容超出保质期 When 被查询或引用 Then 标注为**可能过期**
- Given 一条内容被标注过期 When 生成答案 Then 允许使用但必须标注
- Given 内容被改动 When 完成 Then 原核验记录**保留为历史**，
  新状态为「未核验」——改过的东西不能沿用旧的核验结论

### 输出侧的硬规则

- Given 生成任何答案 When 输出 Then 必须给出所依赖内容中**未核验的比例**
- Given 某内容的状态为「已驳回」 When 生成答案 Then **不得使用**
- Given 一个答案完全建立在未核验内容之上 When 输出 Then 允许，
  但必须在显著位置说明
- Given 一个答案 When 输出 Then 必须标注它用了哪些依据、
  哪些是编审级、哪些只是单源

## 验收标准

- [ ] 导入内容默认状态为「未核验」
- [ ] 自动预检通过的状态与已核验状态在数据与输出中均可区分
- [ ] 未核验内容被引用时输出中有可见标注
- [ ] agent 的交叉校验结论是提议，不直接改变可信度判断
- [ ] 核验记录生效必须有人拍板，且记录批准者与理由
- [ ] 每条核验记录能回答「谁、何时、凭什么、核验到哪一部分」
- [ ] 只有状态没有理由的核验记录被拒绝
- [ ] 提出者与批准者分别标识
- [ ] 核验记录不进入任何队列
- [ ] 以「实测」核验但缺少版本、配置或样本数时被拒绝
- [ ] 实测样本数为 1 时被标记为「单样本」
- [ ] 重算得到的可信度不高于其依赖链上的最低可信度
- [ ] 互相引用或转载的两个来源不被计为两个独立证据
- [ ] 文本高度雷同的来源被标记为「可能同源」
- [ ] 「多源」记录缺独立性判定结果时被视为「编审」
- [ ] 独立来源只有一份时不呈现为「多源一致」
- [ ] 支持记录「依据已核验、结论未核验」
- [ ] 只核验部分限定条件时未覆盖的部分仍标记未核验
- [ ] 主观判断只核验依据是否充分，不声称结论已验证
- [ ] 冲突内容均标记为有争议且系统不自动择一
- [ ] 争议裁决走歧义裁决并记录依据、裁决者与时间
- [ ] 来源修订变化后相关内容标为「依据已变」
- [ ] 内容被改动后原核验记录保留且新状态为未核验
- [ ] 已驳回的内容不出现在任何输出中
- [ ] 每个答案输出都包含未核验比例
- [ ] 答案为编审级或单源时被标注

## 边界与异常

- 核验人未标识：**拒绝**记录核验（无追责的核验等于没有核验）
- 批准者不是人（是 agent）：**拒绝**
- 核验时间缺失或早于内容导入时间：拒绝
- 同一内容被两人同时核验且结论相反：两条并存，标记争议，不自动择一
- 依据不可达（来源被删、链接失效）：已核验状态保留，但标注「依据不可达」
- 自动检查发现与已有内容冲突：不自动裁决，登记为歧义并标记争议
- 依据本身是一条已驳回的内容：拒绝作为依据
- 来源是另一条未核验内容：允许，但可信度**不得提升**
- 整批导入中部分条目已被核验：已核验条目不被覆盖，冲突时登记为歧义
- 空核验记录（只有状态没有理由）：拒绝
- 一条内容没有任何核验记录而被答案引用：允许，但答案的未核验比例必须体现它
- 一个项目的核验记录为零：允许；界面说明后果——
  所有输出的未核验比例都是 100%

## 前后端契约

核验记录是本底座对外的**唯一**接口面。它挂在各自所属的部件服务上，
不单独设界面（见 `workspace.spec.md` 的「页面与服务的对应」）。

| 方法 | 所在服务 | 参数 | 返回 | 说明 |
|---|---|---|---|---|
| `Verifications` | 按标的所属部件 | `ref, limit` | `VerificationView[]` | 某个标的的全部核验记录，时间倒序 |
| `ProposeVerification` | `AgentService` | `ref, method, evidence, note` | `Proposal` | Agent 提出核验，进入待拍板 |
| `Verify` | 按标的所属部件 | `ref, by, method, reason, evidence` | `VerificationView` | 人直接核验（他本人即批准者） |
| `Reject` | 按标的所属部件 | `ref, by, reason` | `VerificationView` | 驳回；条目保留 |
| `Independence` | 按标的所属部件 | `a, b` | `IndependenceView` | 两个来源是否独立；给出判定依据 |
| `Unverified` | `WorkspaceService` | — | `UnverifiedView` | 全项目的未核验分布，供界面汇总呈现 |

`VerificationView`：

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `ref` | string | 否 | 标的标识（数据、文档、经验等） |
| `method` | string | 否 | `measurement` / `recompute` / `multisource` / `editorial` |
| `methodText` | string | 否 | 中文说明（实测 / 重算 / 多源 / 编审） |
| `proposedBy` | `ActorView` | 否 | 提出者，可以是 agent |
| `approvedBy` | `ActorView \| null` | 是 | 批准者；null 表示尚未生效（还在待拍板） |
| `reason` | string | 否 | **必填** |
| `evidence` | string | 否 | 依据 |
| `version` / `config` / `samples` | string | 否 | 实测必填；`samples` 为 1 时标单样本 |
| `chain` | `string[]` | 否 | 重算的推导链 |
| `sources` | `SourceView[]` | 否 | 多源的各来源 |
| `independence` | `string` | 否 | 多源的独立性判定结果 |
| `scope` | string | 否 | 核验到哪一部分：`all` / `basis-only` / `partial` |
| `scopeNote` | string | 否 | 部分核验时说明未覆盖什么 |
| `at` | string | 否 | RFC3339 |
| `supersededBy` | string | 否 | 被哪条新记录取代；空串表示没有 |

`IndependenceView`：`{ independent: bool, kind, why }`
——`kind` 为 `cite`（互相引用）/ `reprint`（转载）/ `similar`（文本雷同）/ `none`；
`why` 是判定依据，必须给出。

`UnverifiedView`：`{ total, unverified, ratio, byMethod: map[string]int, disputed, rejected }`

约定：

- `Verify` 的 `by` 在服务层校验必须是人；agent 走 `ProposeVerification`
- 每条记录必须能回答「谁、何时、凭什么、核验到哪一部分」；
  `reason` 为空或 `scope` 缺失时拒绝写入
- **没有**「待核验队列」接口：本底座不提供返回「等人核验的清单」的方法。
  需要人动手的是待办区的待拍板与待裁决
- `Independence` 必须给出 `why`：只说「不独立」而不说为什么，人无法复核这个判断

## 待确认

1. 核验人的身份如何界定：本机单一用户，还是需要多角色与权限
2. 内容改动后是否一律回到「未核验」，还是区分「改错别字」与「改结论」
3. 保质期到期是自动转为未核验，还是仅标注为可能过期
4. 是否需要「核验签名」来防止事后篡改核验记录
5. 来源为**多人维护、有编辑历史与回退机制**的结构化数据时，
   其既有编辑审核是否可作为「编审」级依据的一部分
   ——**倾向于可以，但不得升格为实测或多源**
6. 未核验比例的呈现阈值：达到多少时必须在输出显著位置说明（当前：完全建立在未核验上才必须显著说明）

## 附：一个已实测的反例

本项目实测发现：某 wiki 的定义声明 13 个字段，实际数据中出现 15 个（多出两个未声明字段）；
同时定义中允许的 `stats` 字段在 281 条记录里有 276 条是空对象。

这说明两件事，正是本规格要防的：

1. **「经过人工编辑维护」不等于「已被核验」**——多人维护的结构化数据照样会漏、会漂移。
2. **「字段存在」不等于「内容已被核验」**——空字段与有值字段在核验意义上完全不同。
