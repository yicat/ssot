# 核验：人工验证与可信度

## 目的

保证进入事实源的内容**可信度可见、可追溯、可追责**。

系统中有大量内容来自非权威渠道（社区攻略、玩家实测、二手转载）。这些内容不能因为「被采集进来」就被当作事实使用。

本层定义：**什么算核验、谁能核验、核验到什么程度、未核验的内容如何使用**。

核心立场：**系统不能让内容"看起来已经核验过"**。默认一切未核验；未核验内容**允许使用，但必须可见**。

## 术语

- **断言**：一条事实或建议的最小单位（见 `semantics-design.md`）。
- **依据（evidence）**：支持该断言的东西——实测样本、官方文案、统计数据、可重算的推导。
  **依据 ≠ 来源**：来源是「谁说的」，依据是「凭什么这么说」。
- **核验（verification）**：对断言的可信度做出的、**有记录的人工判断**。
- **核验方法**：得出该判断的手段，分四级（见下）。方法不同，可信度不同。
- **独立来源**：彼此不存在引用、转载或同源关系的来源。**不独立的多个来源不是多个证据。**
- **部分核验**：只核验了断言的某一部分（例如依据可信但结论未验证）。
- **争议（disputed）**：两条或多条断言互相冲突且尚未裁决。

## 核验方法分级（强度从高到低）

| 级别 | 方法 | 含义 | 必须同时记录 |
|---|---|---|---|
| 1 | **实测** | 在游戏内实际观测 | 版本、双方配置、样本数、是否可复现 |
| 2 | **重算** | 由其他已核验断言推导且结果一致 | 推导链 |
| 3 | **多源** | 多个**独立**来源一致 | 各来源及其独立性判定结果 |
| 4 | **编审** | 人工阅读后判断接受 | 核验人、理由 |

**四级不得互相等同。** 尤其是「编审」——它是人工判断，不是验证。

## 领域规则（Given-When-Then）

### 默认未核验

- Given 任何外部内容被导入 When 入库 Then 其核验状态为「待核验」，**不得默认视为已核验**
- Given 自动预检（格式、引用完整性、可否重算、是否与已有断言冲突）通过 When 记录 Then 状态为「已自动预检」，**不得等同于已核验**
- Given 一条未核验断言 When 被方案引用 Then 方案输出必须**显式标注**该断言未核验

### 核验方法的记录要求

- Given 一条断言以「实测」记录核验 When 缺少版本、配置或样本数 Then **拒绝**该核验记录
- Given 实测样本数为一 When 记录 Then 允许但标记「单样本」，其可信度低于多样本
- Given 一条断言以「重算」记录核验 When 推导链上存在未核验断言 Then 记为该链的最低可信度，**不得高于其依赖**
- Given 仅有单一来源 When 人工接受 Then 方法必须记为「编审」，可信度**不得等同于**实测或多源

### 独立性判定

- Given 来源 A 引用了来源 B When 判定独立性 Then 二者**不独立**，合并为一个证据
- Given 两个来源的文本高度雷同 When 判定独立性 Then 标记为「可能同源」，不作为独立证据
- Given 多个来源发布时间相近且内容雷同 When 判定 Then 标记为可疑，转人工确认
- Given 判定为不独立的多个来源 When 记录核验 Then 证据数计为一

### 部分核验

- Given 一条断言的依据可核验而其结论不可核验 When 核验 Then 允许记录「依据已核验、结论未核验」
- Given 一条断言带多个限定条件而只核验了其中一部分 When 核验 Then 未覆盖的条件仍标记为未核验
- Given 一条断言包含主观判断（例如「某式神在此活动中很强」） When 核验 Then **只核验依据是否充分，不声称结论已被验证**

### 争议与裁决

- Given 两条断言冲突 When 核验 Then 二者**均**标记为「有争议」，**不得自动择一**
- Given 争议被裁决 When 记录 Then 必须记录裁决依据、裁决人、时间
- Given 分歧无法裁决 When 记录 Then 保留争议状态，**不得强行给出结论**

### 重核验的触发

- Given 来源内容的修订标识发生变化 When 系统检测到 Then 由该来源产出的断言全部转为「待重核验」
- Given 一条断言超出保质期 When 被查询或引用 Then 标注为可能过期
- Given 一条断言被标注过期 When 生成方案 Then 允许使用但必须标注

### 人力的分配

- Given 待核验条目多于可投入人力 When 排序 Then 依据**影响面**（被引用次数）、断言类型、是否争议、变更频率排序
- Given 排序队列 When 生成 Then 必须包含**随机抽检**项，以防只核验了"显眼"的部分而遗漏系统性问题

### 输出侧的硬规则

- Given 生成任何方案 When 输出 Then 必须给出该方案所依赖断言中**未核验的比例**
- Given 某断言的核验状态为「已驳回」 When 生成方案 Then **不得使用**
- Given 一个方案完全建立在未核验内容之上 When 输出 Then 允许，但必须在显著位置说明

## 验收标准

- [ ] 导入内容默认状态为「待核验」
- [ ] 自动预检通过的状态与已核验状态在数据与输出中均可区分
- [ ] 未核验断言被引用时，输出中有可见标注
- [ ] 以「实测」核验但缺少版本、配置或样本数时被拒绝
- [ ] 实测样本数为 1 时被标记为「单样本」
- [ ] 重算得到的可信度不高于其依赖链上的最低可信度
- [ ] 互相引用的两个来源不被计为两个独立证据
- [ ] 文本高度雷同的来源被标记为「可能同源」
- [ ] 支持记录「依据已核验、结论未核验」
- [ ] 冲突断言均被标记为有争议，且系统不自动择一
- [ ] 裁决记录包含依据、裁决人、时间
- [ ] 来源修订标识变化后，相关断言转为「待重核验」
- [ ] 已驳回的断言不出现在任何方案输出中
- [ ] 每个方案输出都包含未核验断言的比例
- [ ] 核验队列可按优先级排序，且包含随机抽检项
- [ ] 每条核验记录都能回答「谁、何时、凭什么、核验到哪一部分」

## 边界与异常

- 核验人未标识：**拒绝**记录核验（无追责的核验等于没有核验）
- 核验时间缺失或早于内容导入时间：拒绝
- 同一断言被两人同时核验且结论相反：两条并存，标记争议，不自动择一
- 依据不可达（链接失效、页面被删）：已核验状态保留，但标注「依据不可达」
- 自动预检发现与已有断言冲突：不自动裁决，直接进入人工队列并标记争议
- 依据本身是一条已驳回的断言：拒绝作为依据
- 来源是另一条未核验断言：允许，但可信度不得提升
- 核验后内容被修改：状态**回到待核验**，原核验记录保留为历史
- 整批导入中部分条目已被核验：已核验条目不被覆盖，冲突时进入人工队列
- 空核验记录（只有状态没有理由）：拒绝

## 前后端契约

**待定**，取决于对外接口形态。已确定的约束：

- 核验是**人工动作**，必须能记录操作者身份与时间
- 方案输出必须携带其所依赖断言的未核验比例
- 核验工作台需要能高效处理队列：按优先级浏览、批量处理、比较冲突双方、查看依据原文与出处
- 核验状态与理由必须能被外部读取（不只在界面里可见）

> **这同时回答了此前悬置的问题：图形界面的主要用途不是数据录入，而是核验工作台。**
> 数据由程序导入，人只在核验环节介入。

## 待确认

1. 核验人的身份如何界定：本机单一用户，还是需要多角色与权限？
2. 核验后修改内容是否一律回到「待核验」，还是区分「改错别字」与「改结论」？
3. 随机抽检的比例，以及抽检发现问题时是否追溯同批内容？
4. 保质期到期是自动转「待核验」，还是仅标注为可能过期？
5. 是否需要「核验签名」来防止事后篡改核验记录？
6. 来源为**多人维护、有编辑历史与回退机制**的结构化数据（例如 wiki 的 Data 命名空间）时，
   其既有编辑审核是否可作为「编审」级依据的一部分？——**倾向于可以，但不得升格为实测或多源。**

## 附：一个已实测的反例

本项目实测发现：某 wiki 的 schema 声明 13 个字段，实际数据中出现 15 个（多出两个未声明字段）；
同时 schema 中允许的 `stats` 字段在 281 条记录里有 276 条是空对象。

这说明两件事，正是本 spec 要防的：

1. **「经过人工编辑维护」不等于「已被核验」**——多人维护的结构化数据照样会漏、会漂移。
2. **「字段存在」不等于「内容已被核验」**——空字段与有值字段在核验意义上完全不同。
