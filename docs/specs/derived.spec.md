# derived.spec.md —— 水面下的派生层（KV / 关系 / 图 / 向量）

主题：**用户只看见文档与数据表，其余由系统自动维护**。
借的是 LightRAG 的机制（见 `docs/notes/oss-comparison.md` §三），但按我们的立场改造。

> 一句话：**事实只存在文件里**（`docs/` `raw/` `tables/` 是唯一事实源）；
> 底下的 KV、实体关系图、向量全是**派生物**——可重建、不进 git、不进人眼。

## 〇、决策规则：机制冲突时**以 LightRAG 为准**

用户定的口径：**LightRAG 是好论文，机制上有冲突就按它来。** 落地时按这个次序判断：

1. **机制（怎么做）→ 以 LightRAG 为准**：切块方式与参数、抽取产物与轮次、存储的抽象划分、
   检索模式与默认值、合并/总结的触发阈值——照它的来，不另外发明。
2. **立场（承诺什么）→ 不自动跟随**：`vault.spec.md` 那几条是产品本身
   （冲突并列不裁决、发布必须是人、未核验可见）。LightRAG 里**没有这几个概念**，
   所以「以它为准」在这里没有可对照的对象；真要让位，先说清后果再改，不默默改。
3. **我们的溯源要求是叠加，不是冲突**：LightRAG 的 `source_id` 到 chunk、多来源还拼成一个字符串
   且会被上限截断；我们在此基础上**每条都带 `doc` + 行号区间**——加一层，不改它的机制。

⚠️ 下面凡标 **[按 LightRAG]** 的都是照它实施；标 **[待定]** 的是真冲突、需要拍板。

## 一、分层（水面上下）

```
用户看得见的（水下、可重建、不进 git）
  docs/  raw/  tables/        ← 唯一事实源；写入即 commit（vault.spec.md §5）
────────────────────────── 水面 ──────────────────────────
  .data/index.db              ← 派生层：KV / 图 / 向量 / 状态，全是表
    docs / links / tables_meta / meta   现有四张（检索是 LIKE，没有分块）
    chunk(id, doc, from_line, to_line, text, status, hash)      分块（**新增**；块自带行号区间）
    embedding(owner_kind, owner_id, dim, vec)                   向量（chunk / doc / entity / relation）
    entity(id, name, type, status, doc, line, ...)              实体（带块级溯源）
    relation(src, dst, keywords, desc, status, doc, line, ...)   关系
    sync(doc, hash, mtime, built_at, stale)                     自动维护的状态
```

> ⚠️ 现状**没有** `chunks` 表：检索只在 `docs.body` 上做 `LIKE`（`vaultindex` 里就 `docs`
> `links` `tables_meta` `meta` 四张 + 每张数据表一张）。所以分块与嵌入都是**要新增**的东西，
> 不是「现有表的扩展」。

- **唯一事实源仍是文件**：删掉 `.data/` 应当只损失检索质量，不损失任何内容。
- **不进 git**：与 `vault.spec.md` §4/§5 一致（`.data/` 永不提交）。
- **不做「影子真相」**：派生层里的任何一条都要能回指到「哪篇文档的哪一段」，
  回指不到的一律不允许存在——否则它就成了一份没有出处、却看起来像事实的东西。

## 二、从 LightRAG 借什么、改什么

| LightRAG 的做法 | 我们怎么改 | 为什么 |
|---|---|---|
| 实体（`entity_name` / `entity_type` / `entity_description`）+ 关系（`source` / `target` / `keywords` / `description`）+ 类型指引（不合用就 `Other`）+ 段落上下文 | **[按 LightRAG]** 字段与提示词结构照借；每条**加** `doc` + 行号区间 + `status` | 它是 chunk 级溯源；我们要能落到具体段落，还要能看出「这条来自未核验文档」 |
| **gleaning 多轮补抽**（`DEFAULT_MAX_GLEANING = 1`） | **[按 LightRAG]** 首轮 + 补抽轮 | 一轮抽不全，它这个机制是实测有效的做法 |
| 同名实体的**多来源描述用 LLM map-reduce 总结**（`_handle_entity_relation_summary`；触发：描述数 ≥ `DEFAULT_FORCE_LLM_SUMMARY_ON_MERGE = 8` 强制；`summary_max_tokens = 1200`、`summary_context_size = 12000`） | **[待定]** 见 §九：它的提示词其实是「冲突时**调和或并列 + 标注不确定性**」，不是"抹掉一边"；但它最终只存**一段合成文本** | 这一段是我们的立场（并列不裁决）与它的机制**唯一的正面冲突**，要拍板 |
| 多来源拼成一个字符串、且会被上限截断 | 关联用**行**表示（一对多），不拼串；来源仍可点开看原文 | 拼串会丢来源、还会被截断。**这是叠加不是改机制** |
| KV / 向量 / 图 / 文档状态四种存储 | **[按 LightRAG]** 四类存储的**抽象照搬**（各自可换实现）；落地实现全放进一个 SQLite（`.data/index.db`）——**向量照存照用**（`embedding` 表 + 进程内暴力扫，实测数字见 §三） | 抽象照它、实现不引服务：一个文件好重建、好备份、好删；我们的规模不需要向量库服务，也不需要 ANN 那种近似索引 |
| 检索模式 `local / global / hybrid / naive / mix`（默认 `mix`；`top_k`、`chunk_top_k = 20`、`related_chunk_number = 5`、KG→chunk 取法默认 `VECTOR`） | **[按 LightRAG]** 五种模式与这组默认值照搬；**但不做生成**——检索结果给人或给 agent 看 | 我们要的是「找得到」，不是它那套问答输出 |
| 强制 LLM + embedding（抽取与总结都要调模型） | **抽取由 agent 任务做**（复用已接好的后端），embedding 在本进程内跑 | App 不做 agent 框架（`agent.spec.md` 定位）；同一套后端换成别的也不影响这层 |

## 三、文档与分块的 embedding（要嵌什么、怎么切）

**嵌「块」，不是整篇当主力**——整篇一条向量只能回答「哪篇相关」，回答不了「哪一段说了」，
而我们要的恰好是后者（块级溯源）。

| 嵌什么 | 怎么嵌 | 为什么 |
|---|---|---|
| **文档分块**（主力） | 每篇按「标题层级 → 空行」切块；每块一条向量，块自带 `doc` + `fromLine/toLine` | 命中能直接落到行；块首拼上「文档标题 · 小节标题」再嵌入，让向量别丢上下文 |
| **整篇**（一条/篇） | 标题 + 摘要式开头（或前 N 块向量取平均） | 只用于「找相似文档」；一篇一条，成本几乎为零 |
| 数据表 | **不嵌数字**；表旁边的说明文本（`tables/README.md` 那种）照嵌 | 数字要算不要"像"——那是 SQL 的活 |
| 实体 / 关系 | 抽出来之后各嵌一条（LightRAG 的做法） | 支撑图上检索 |

**切块口径 [按 LightRAG]**（对着本机那份 clone 读的默认值，不是照记忆）：

- **按标题／段落做语义合并**：它这版用的是 paragraph-semantic chunker，注释里写明
  「heading-aligned paragraph merging needs more」——正好与我们要的「标题 → 空行」一致，不算冲突。
- 目标块大小 **`DEFAULT_CHUNK_P_SIZE = 2000`** token；嵌入重叠
  **`DEFAULT_EMBEDDING_CHUNK_OVERLAP_TOKEN_SIZE = 100`** token。
- 块的 `doc` + 行号区间必须与文件对得上（**文件行号**，与 `vaultfs` 的 `bodyOffset` 同一套）——这是叠加。
- 整块不重叠的部分仍然要留：重叠只用于**嵌入**，正文命中按块自己的行号区间报（免得同一段报两次）。
- ⚠️ **[待定] 2000 token 的块 × 512 token 的嵌入模型**：LightRAG 默认配的是长上下文嵌入
  （bge-m3 那类 8192）；我们选的是 bge-small-zh-v1.5，上限 **512 token**。
  照它的默认值，每块嵌入会被截断到 512、召回变差。两条路（§九.1）：
  ① 换长上下文嵌入模型（体积远大于 39MB，**未实测**，得先 spike）；
  ② 保持 bge-small-zh，块按 512 token 封顶（明确偏离它的默认值）。

**模型与运行时**（已实测，数字与三个坑见 `docs/notes/embedding-spike.md`）：
`Xenova/bge-small-zh-v1.5` 的 int8 ONNX（22.9MB）+ 官方 `onnxruntime.dll`（15.7MB）≈ **39MB**；
512 维，**CLS 池化 + L2 归一**；**0.8ms/条**（含分词）；与 transformers.js **逐位一致**（cos=1.000000）。
⚠️ 那份笔记里的三个坑（purego 在 Windows 编译不过要换绑定、`sugarme/tokenizer` 的
`NewTokenizerFromFile` 是空壳、依赖版本会被缓存带偏）与「对拍必须逐条跑」都照它执行。

**查询仍然必须确定**：`vault.spec.md` 要求「同一份 vault 同一次查询，结果顺序永远一样」，
所以向量检索也要确定——相似度阈值 + 稳定排序，**不许有随机**；混合检索的融合权重写死。

**状态照带**：块向量也带来源文档的 `status`；`draft` 来源的命中在结果里要能看出来。

**向量存哪、怎么搜（已实测）**：

向量**就在这个 SQLite 里**（`embedding` 表，`vec` 存 float32 的 BLOB），相似度在**进程内暴力扫**
——不引 `sqlite-vec` 之类的加载扩展、不引 Milvus/Qdrant 那类服务、不引 Python。
「四种存储收进一个 SQLite」说的是**容器**，不是把向量删掉：**向量是四种里的第三种**。

**为什么敢暴力扫**（512 维、归一化后点积即余弦、`CGO_ENABLED=0`，50 次查询取平均）：

| 规模 | 内存 | 每次查询 |
|---|---|---|
| 1,000 条 | 2.0 MB | **0.23 ms** |
| 10,000 条 | 19.5 MB | **1.99 ms** |
| 100,000 条 | 195.3 MB | **20.15 ms** |

demo 现在的量（407 篇 × 约 10 块 ≈ 4 千条块向量，再加实体/关系）落在 **~2 ms** 那一档。
而且 ANN 是**近似**索引——它会破坏 `vault.spec.md` 那条「同一次查询结果顺序永远一样」；
暴力扫天然确定，与我们的立场一致。

**边界（诚实写下来）**：到 **~10 万条**（≈ 1 万篇文档）时单次约 20 ms、内存约 200 MB，
就该动手了，顺序是：① 先用 FTS / 图邻居把候选缩小，再对候选算向量（混合检索本来就这么做）；
② 再把向量量化成 int8（内存与带宽砍 4 倍，召回基本不掉）；③ 到那时才谈 ANN 索引。
**在那之前不上 ANN**——多一层近似、少一分可复现，不值。

**没定**（见 §六）：块大小最终值、整篇向量要不要、**39MB 随包内置还是首次运行下载**、
向量先上不上；以及 §九 的两条待拍板。

## 四、自动维护（「自动处理」的落地）

1. **写入即失效**：文档/表一变，它在派生层里的条目立刻标 `stale`（不假装还准）。
2. **后台重建**：抽取与嵌入都是后台任务，**不挡人的操作**（界面可继续读文档）。
   任务失败就留 `stale` + 原因，**不静默**——「未核验必须可见」的同一条立场。
3. **增量而非全量**：按 `sync(doc, hash)` 判断哪几篇变了，只重抽这几篇。
4. **半成品也标出来**：正在抽/抽失败/嵌入缺失，界面上是一条**状态**（水面上的极小一块），
   不是一屏配置。

## 五、与已定规范的关系（不许破的四条）

1. **事实只在文件里**：派生层永远可以删掉重建；任何「只在派生层里」的内容都不算事实。
2. **冲突并列**：实体/关系的描述并列保存，谁都不许"总结"掉谁。
3. **未核验可见**：派生条目带来源文档的 `status`；检索结果里 `draft` 来源要能看出来。
4. **块级溯源**：每条派生条目带 `doc` + `line`（文件行号，能直接跳过去）。

## 六、未定

1. **抽取的触发方式**：写入后就排队，还是空闲时批量，还是显式「重建索引」。
   （倾向前两者都有：小改动排队、大批量走显式。）
2. **文档 embedding 的几个具体值**：块大小（先按 400 字）、整篇向量要不要、
   **39MB 模型随包内置还是首次运行下载**（体积敏感分发的取舍见 `embedding-spike.md` §六）。
3. **向量检索的引入时机**：
   已验证可行（bge-small-zh-v1.5 int8 22.9MB + ONNX Runtime 15.7MB，进程内、无 cgo、
   0.8ms/条，与 transformers.js 逐位一致；数字与三个坑见 `docs/notes/embedding-spike.md`），
   但**先上不上**没定——现在 FTS（LIKE）+ 图邻居已经能覆盖一部分召回。
4. **抽取用什么提示词、抽几类实体**：这不是数据模型问题，是质量与成本问题，得先跑一批看。
5. **WeKnora 那几条怎么落**：`superseded_by`（被取代）与「引用失效」其实都是**图上的边**，
   可以直接长在这层里，不必新增用户可见概念（待一起定，见 `docs/notes/oss-comparison.md` §五）。
6. 界面上「索引状态」给多少信息（一行？可展开？）。

## 七、不做

- **不做问答/RAG 生成链**：检索结果给人或给 agent 看，由它们自己读文档；我们不生成"答案"。
- **不让 LLM 裁决冲突**（LightRAG 那条反面）。
- **不让未核验内容以同等地位进库**（MaxKB 那条反面）：派生条目必须带来源状态。
- 不引入外部向量库服务、不引入 Python 运行时：一切落在 SQLite + 纯 Go 进程内。

## 八、怎么验证

- **可重建**：删掉 `.data/index.db` → 重建 → 检索结果与之前一致（同一份 vault、同一次查询，
  结果顺序确定——`RankHits` 已经保证确定性）。
- **不漏**：每篇 `docs/`+`raw/` 文档都要在 `sync` 表里有记录（`stale=false`）。
- **能回指**：随机抽 20 条实体/关系，`doc`+`line` 必须真的指向那段文字（用
  `resolve` 的块锚点解析验，行号是**文件行号**）。
- **不洗白**：从 `draft` 文档抽出来的条目，检索结果里必须带 draft 标记。
- **不裁决**：同一实体的两条不同描述必须**都在**（数量对得上，且各自带来源）。
  ⚠️ 这条**取决于 §九.2 的拍板**：若按 LightRAG 只存一段合成描述，这条要改成
  「合成描述 + 每条来源可点开看原文」。

## 九、[待拍板] 「以 LightRAG 为准」撞到我们立场的那两处

### 1. 块大小 2000 token × 嵌入模型上限 512 token

LightRAG 默认 `DEFAULT_CHUNK_P_SIZE = 2000`（它配的是长上下文嵌入，如 bge-m3 8192）；
我们选的 bge-small-zh-v1.5 上限只有 512 token，照它的默认值每块会被截断。

| 选项 | 代价 |
|---|---|
| **A. 换长上下文嵌入模型**（照 LightRAG 默认） | 体积远大于现在的 39MB（**未实测**，要先照 `embedding-spike.md` 的办法 spike 一遍：体积 / 速度 / 与参照实现逐位一致） |
| **B. 保持 bge-small-zh，块按 512 token 封顶** | 明确偏离它的默认值；但块更小、命中更准（块级溯源本来就更细），且不欠新债 |

### 2. 同名实体的多来源描述：合成一段，还是并列两条

- LightRAG：`_handle_entity_relation_summary` 用 LLM **map-reduce 总结**成**一段**文本
  （描述数 ≥ 8 强制总结；`summary_max_tokens = 1200`）。它的提示词里对冲突的要求是
  「**调和，或并列呈现并标注不确定性**」——**不是"抹掉一边"**；但最终存储只留那段合成文本，
  原始描述只还在 chunk 里。
- 我们的已定立场（`vault.spec.md` §6）：**并列保存、系统不裁决**。

| 选项 | 结果 |
|---|---|
| **A. 照 LightRAG** | 图上只有一段合成描述（保留每条来源可点开）。代价：「系统不裁决」这句在**图上**不再成立——裁决者变成 LLM |
| **B. 照 LightRAG 的机制 + 保留并列**（推荐） | 存两样：`description_summary`（LLM map-reduce 合成，参数与阈值照它）+ `description[]`（每条原文 + `doc`/行号，并列保留）。检索与展示默认用 summary，点开看并列原文 |
| **C. 只并列，不合成** | 等于不采纳它这条机制（与「以 LightRAG 为准」相悖，除非你要求） |

⚠️ 提醒一句（MaxKB 那条教训）：无论选哪个，合成文本都**必须带来源状态**——
从 `draft` 文档合成出来的描述不能在界面上看起来像"已确认的事实"。
