# 架构：平台、项目与 Case

## 目的

上一版把整个系统组织成「断言 + 可信度分级 + 核验队列」，主线是**数据可信度**。
那条主线不是错的，但它不是**主线**：

- 真正要解决的问题是「把一堆来源整理成可用的 SSOT」，而整理这件事的主体是 **Agent**，
  不是一条要人去排队的流程。核验只是 Agent 会做的一个动作（交叉校验），不是产品骨架。
- 上一版里没有任何位置放「Agent」——那才是最大的缺口。
- 上一版把「场景」写成一份 YAML 配置（requires / inputs / outputs）。可你要的是一个
  **有上下文的子 Agent**：它知道自己在干什么、核心数据与核心文档是哪些、正常情况下怎么用。

本纲重立三层与每层的归属物，并明确**谁能写什么**。这是全项目最先要立住的东西：
部件规格都可以改，权限边界不能模糊。

## 术语

- **平台**：同时承载多个项目的运行时（项目选择、Agent 运行时、工具执行环境）。
- **项目**：一个领域（例如阴阳师）。**隔离边界**：定义、数据、文档、词表、会话、Case 都不跨项目。
- **部件**：项目下的六件东西——主对话 Agent、工具、文档、词表、DataSchema、项目基础数据。
- **Case**：项目下的一个用途，**每个 Case 就是一个子 Agent**。它有自己的上下文、经验与数据表。
- **主对话 Agent**：项目级 Agent，支持多个会话。它是项目级六部件的**建设者与维护者**。
- **Case 子 Agent**：只读项目级六部件，只写自己的 experience 与 CaseData。
- **底座**：断言模型（主体 / 谓词 / 取值 / 限定条件 / 来源 / 溯源 / 分级）与准入、核验记录等
  底层机制。它们仍在，但**不再是使用者直接面对的流程**。

## 领域规则（Given-When-Then）

### 三层与归属

- Given 一个平台 When 使用 Then 支持多个项目；项目之间互不可见
- Given 一个项目 When 建立 Then 它包含六个部件：主对话 Agent、工具、文档、词表、
  DataSchema、项目基础数据
- Given 一个项目 When 建立 Case Then Case 归属该项目，且**主对话 Agent 参与建立**
- Given 两个 Case When 并存 Then 它们的 experience 与 CaseData **互不可见**；
  项目级六部件是它们**唯一共享**的东西
- Given 一个 Case When 建立 Then 它必须有一份**上下文**：干什么事、核心数据是哪些、
  核心文档是哪些、正常情况下怎么用

### 写入权限

这是本纲最硬的一条：**项目级只有一个写入口。**

- Given 主对话 Agent When 工作 Then 可以建立与修改项目级的六个部件
- Given Case 子 Agent When 运行 Then **只能读**项目级六部件；只能写自己的 experience 与 CaseData
- Given Case 发现项目级内容有问题（词表指代错了、DataSchema 缺字段、基础数据有误、文档不该这么总结）
  When 记录 Then 写进自己的 experience，**不得直接改项目级**；由主对话 Agent 汇总后统一改
- Given 一次项目级修改 When 落盘 Then 必须能回答四件事：谁改的、何时改的、凭什么改、改前是什么
- Given 项目级内容 When 被 Case 读取 Then 读的是**当时那一版**；此后项目级再变更，
  受影响的 Case 产物必须标出「依据已变」，**不得静默沿用**
- Given 权限判定 When 执行 Then 在**服务层**强制，不依赖界面隐藏按钮——
  界面能绕过的边界等于没有边界

### 六部件各自的职责（避免混用）

四件最容易混的东西，用一条判据分开：**这段内容能不能确定地写出「主体—关系—取值」。**

| | 判据 | 落在哪 |
|---|---|---|
| 能确定地抽出主体—关系—取值 | 例如「某技能一段伤害倍率 = 80%」 | DataSchema 定义 + 项目基础数据承载 |
| 抽不出、或抽了就失真 | 机制说明、规则原文、改动公告 | **文档** |
| 说的是「我们讲的这个词指什么」 | 同义、多义、条件指代、词间关系 | **词表** |
| 说的是「怎么算」 | 加算还是乘算、取整方式、顺序 | **项目基础数据**（计算方式本身是数据） |

- Given 一份内容 When 归类 Then 只能落一处；**不得为了「变成数据」而强行拆**
- Given 一个 DataSchema 定义 When 建立 Then 必须带**具体的使用文档**，
  写清它什么时候用、什么时候不能用；**不得混用**（两份定义说同一件事而口径不同 → 报冲突，不自动择一）
- Given 一个 DataSchema 定义 When 建立 Then 它的表述要有**确定性**：
  给定同一份来源与同一套定义，两个人抽出同一个结论
- Given 计算方式（公式）When 需要 When 使用 Then 必须**在项目里声明**，
  不得硬编码在代码里——它要能被核验、被版本化、被替换
- Given 词表中的一个词 When 出现 Then 它可能指多个东西（多义）；
  也可能是多个词指同一个东西（同义）；**有的还要看上下文才知道指哪个（条件指代）**

### 底座：断言仍然在，但不再挡在人前面

- Given 项目基础数据 When 存储 Then 用**断言**表示（主体、谓词、取值、限定条件、来源、溯源、分级）
- Given 限定条件不同的两条断言 When 并存 Then 互不覆盖——同一件事在不同条件下不同效果，
  那是指代/条件问题，不是冲突
- Given 同一主体同谓词同限定条件而取值不同的两条断言 When 并存 Then 两条都留，标为有争议，
  **系统不自动择一**
- Given 断言 When 面向使用者 Then **界面上不再有独立的核验队列**：
  交叉校验由主对话 Agent 发起与汇总，核验记录（谁、何时、凭什么）仍然保留
- 保留底座的三个理由：来源可追、冲突可并存、分级让「直引」与「推断」可分辨。
  取消界面的理由：把人固定成流程里的一环，而在这个结构里人负责**提要求与拍板**，
  整理与交叉校验是 Agent 的活

### Agent

- Given 主对话 When 使用 Then 支持**多个会话**；会话是工作记录，
  **不是事实源**——事实源是项目级六部件
- Given 主对话 When 完成一次整理 Then 产出应落到具体部件里（文档 / 词表 / DataSchema / 基础数据），
  而不是只留在会话里
- Given 一个 Case When 运行 Then 按**给入的条件**给出答案；条件不同则答案不同
- Given 一个答案 When 给出 Then 必须能说明它用了哪些数据与哪些文档
- Given Agent 不可用（无网络、无凭据、无额度） Then 项目仍**可读**；
  不得因为 Agent 不可用而让已有内容不可访问

### 演进与不变量

- Given 项目定义变更 When 应用 Then 走迁移流程，既有数据不得被静默改写
- Given 一个项目 When 删除 Then 不影响其他项目
- Given Case 的产物 When 所依赖的项目级内容变更 Then 标注「依据已变」并保留原依据标识
- Given 会话记录 When 很长 Then 允许裁剪，但**不得裁掉「谁改了什么」**

## 验收标准

- [ ] 平台可同时存在多个项目，且一个项目的行为不影响另一个
- [ ] 项目级六部件与 Case 级 experience / CaseData 的归属在数据与界面上都清晰
- [ ] Case 无法写入项目级六部件的任何一处，尝试写入时被拒绝并给出正确路径
- [ ] 一个 Case 看不到另一个 Case 的 experience 与 CaseData
- [ ] 项目级的每次修改都能回答「谁、何时、凭什么、改前是什么」
- [ ] 项目级变更后，引用它的 Case 产物被标为「依据已变」，原依据标识仍可查
- [ ] 界面上没有独立的「核验队列」入口
- [ ] 断言的来源、限定条件与分级在需要时仍可查（底座未丢）
- [ ] 计算方式无法以硬编码形式存在：项目里没有对应声明时，计算结果出不来且说明原因
- [ ] 每个 DataSchema 定义都有使用文档，缺文档时定义不被视为可用
- [ ] 词表能表达同义、多义、条件指代与词间关系
- [ ] 条件指代无法从上下文确定时**记录歧义并报出来**，不猜
- [ ] Case 建立时上下文四项（干什么、核心数据、核心文档、怎么用）缺项被明确标出
- [ ] 空列表 / 无数据都给出「没有 + 这意味着什么」的说明
- [ ] 项目没有 Case、或 Case 没有 experience 时，界面说清这不是错误

## 边界与异常

- 平台无项目：给出明确提示与建立路径，不指向不存在的目录
- 项目加载失败：保持原有上下文不变，返回失败原因，不进入半加载状态
- 两个项目同名不同定义：各自独立，不互相引用
- Case 试图写项目级：拒绝并指出应写进 experience，由主对话 Agent 汇总
- 项目级部件被删除而 Case 仍在引用：保留 Case 内容并标注「依据不可达」，不删除 Case
- Case 上下文引用了不存在的部件：加载时报出，不静默忽略
- 同一份文档被两个 Case 各自总结：两份总结并存，互不覆盖，各自注明依据
- 词表里一个词在同一段上下文里指向两个都说得通的东西：产出歧义记录，
  携带两个候选与原文位置，由人裁决
- Agent 产出与项目级既有内容矛盾：以「提议」形式呈现差异，不直接覆盖
- 会话记录裁剪：只裁过程，保留所有修改记录与结论

## 前后端契约

服务按层划分。**权限在服务层强制**：Case 作用域的服务不得持有项目级写入口。

| 服务 | 作用域 | 可写 |
|---|---|---|
| `PlatformService` | 平台 | 项目注册表（建立/选择/移除项目） |
| `AgentService` | 项目 | 主对话会话：新建会话、追加消息、列出会话、取会话 |
| `ToolService` | 项目 | 工具的登记、执行、组合；**执行结果不是事实源** |
| `DocumentService` | 项目 | 文档的导入、生成、登记新修订、建立关联、段落锚点 |
| `DictService` | 项目 | 词条、同义/多义关系、条件指代规则、歧义记录与裁决 |
| `DataSchemaService` | 项目 | 定义的新增与演进、使用文档、冲突报告 |
| `BasicDataService` | 项目 | 基础数据（断言底座）的写入与查询、公式声明 |
| `CaseService` | Case | Case 的建立与上下文维护 |
| `ExperienceService` | Case | experience 的增删改查（删=标记作废） |
| `CaseDataService` | Case | Case 自己的数据表 |
| `WorkspaceService` | 平台 | 界面所需的聚合视图（只读） |

通用约定：

- 每个写操作返回**改了哪一版**；项目级写操作额外返回**影响面**
  （有多少 Case 产物引用了它，将被标为「依据已变」）
- 读操作返回内容时一并返回其来源与版本标识，使界面可以显示「依据已变」
- Case 作用域的服务在收到针对项目级的写请求时，返回明确错误并指出正确路径
- 无 Agent 可用时，除 Agent 相关服务外其余服务全部可用

## 附一：规格集与既有规格的去向

本纲之下的规格集（按写作顺序）：

1. `architecture.spec.md`（本文）——三层、六部件、权限边界
2. `project.spec.md`——项目的组成、加载、隔离与导出
3. `agent.spec.md`——主对话会话与 Case 子 Agent 的能力边界
4. `tools.spec.md`——工具：声明、执行、组合
5. `document.spec.md`——文档：导入、生成、双向索引、版本、段落锚点
6. `dict.spec.md`——词表：同义、多义、条件指代、词间关系、歧义裁决
7. `dataschema.spec.md`——数据定义：表述、使用文档、冲突、演进
8. `basicdata.spec.md`——项目基础数据：断言底座、公式即数据、质量视图
9. `case.spec.md`——Case：上下文、按条件给答案、只读边界
10. `experience.spec.md`——经验：增删改查与修订历史、上报通道
11. `casedata.spec.md`——Case 数据表
12. `workspace.spec.md`——工作台界面

底座规格（保留，但定位从「产品主线」改为「内部机制」）：

13. `core.spec.md`——断言模型与校验
14. `ingestion.spec.md`——取回、存档、解析
15. `admission.spec.md`——准入
16. `verification.spec.md`——核验记录（取消独立界面）
17. `computation.spec.md`——表达式、量纲与时间
18. `derivation.spec.md`——派生与缓存
19. `decision.spec.md`——歧义的登记与裁决（被 `dict` 与 `dataschema` 共用）

既有规格的具体去向：

| 现有规格 | 去向 | 理由 |
|---|---|---|
| `core.spec.md` | 保留，改写定位 | 断言模型仍在用，但不再挡在人前面 |
| `metamodel.spec.md` | 并入 `dataschema.spec.md` | 原语清单是数据定义的一部分 |
| `migration.spec.md` | 并入 `dataschema.spec.md` | 定义演进属于数据定义 |
| `data.spec.md` | 拆解 | 定义视图→`dataschema`；断言库与质量视图→`basicdata` |
| `project.spec.md` | 改写 | 「定义 + 实例」改为六部件 |
| `document.spec.md` | 改写 | 补双向索引、段落锚点、生成文档、与词表的关系；归属改为项目级（已是） |
| `ingestion.spec.md` | 保留为底座，改写定位 | 取数动作改由工具发起 |
| `admission.spec.md` | 保留为底座 | 写入前的校验仍需要 |
| `verification.spec.md` | 保留为底座，删去产品定位 | 核验记录保留，界面取消 |
| `computation.spec.md` | 保留，改归 `basicdata` 之下 | 公式即数据 |
| `derivation.spec.md` | 保留为底座 | 中间产物与缓存的规则不变 |
| `decision.spec.md` | **保留为底座**，定位改为「歧义的登记与裁决」 | 写 `dict.spec.md` 时发现：歧义不止一种——**指代歧义**（这个词指哪个义项）与**抽取歧义**（这段文本里该取哪个值）。前者是词表的活，后者是数据定义的活。与其把它塞进词表，不如留成两者共用的机制 |
| `scenario.spec.md` | 改写为 `case.spec.md` | Case 是子 Agent + 上下文，不只是配置 |
| `experience.spec.md` | 改写 | 从只追加改为可增删改 + 修订历史；补上报通道 |
| `alternatives.spec.md` | 并入 `case.spec.md` | 「条件不同给不同答案」的多解形态 |
| `player-profile.spec.md` | **待定** | 新结构未提个人档案；需定它是项目级部件、CaseData，还是不要 |
| `workspace.spec.md` | 改写 | 界面随三层与六部件重排 |

## 附二：与上一版的关键差异

| | 上一版 | 本版 |
|---|---|---|
| 主线 | 数据可信度（分级 + 核验队列） | 整理与使用（Agent 建设，Case 使用） |
| 谁在中心 | 核验的人 | 主对话 Agent |
| 人的角色 | 流程里的一环（排队核验） | 提要求、拍板、审阅 |
| 场景 | 一份 YAML 配置 | 一个有上下文的子 Agent |
| 项目内容 | 定义 + 实例数据 | 六部件 |
| 词表 | 只是界面显示用的中文名 | 指代系统（同义、多义、条件指代、词间关系） |
| 计算方式 | 公式文件 | 项目基础数据（公式即数据） |
| 数据写入边界 | 只有准入层一道 | 项目级只有一个写入口；Case 只读 + 上报 |
| 核验 | 独立界面与队列 | Agent 的动作，记录保留 |
