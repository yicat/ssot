# 词表：保证「我们说的东西是一个」

## 目的

同一个东西，项目里会有好几种叫法：文档里写「暴击伤害」，数据定义里是 `crit_factor`，
Case 里说「爆伤」，wiki 上又写成「会心伤害」。系统如果不知道这些是同一件事，
Agent 整理出来的内容就会各说各话——**同一件事在三个地方有三套说法，而没有任何一处能说明它们是一件事。**

反过来，同一个词也可能指好几件事（「攻击」可以是面板攻击、可以是攻击次数、
也可以是某个技能的系数）。还有一批词**要看了上下文才知道指哪个**。

词表就是管这件事的地方。它非常像词典，因此本规格按词典的结构来：

| 词典里的东西 | 这里的对应 |
|---|---|
| 词目（概念） | **词条**，有稳定标识 |
| 词形、异体、简称、外文名 | **词面**，一个词条可以有多个 |
| 多义词的各个义项 | **义项**，一个词面可以对应多个词条 |
| 释义 | 词条自身的说明 |
| 上下位、整体部分、近义、反义、相关 | **词间关系** |
| 语境释义 | **条件指代**：在什么条件下这个词固定指哪个词条 |

## 术语

- **词条（term）**：一个「我们说的东西」。稳定标识与显示名分开。
- **词面（surface）**：用来指它的字样。一个词条可有多个词面（别名、简称、外文名、旧名）。
- **义项（sense）**：一次「词面 → 词条」的映射。一个词面有多个义项时就是多义词。
- **条件指代（conditional reference）**：在特定上下文里，某个词面固定指某个词条。
- **上下文（context）**：判定指代所依据的东西——所在文档、邻近段落、所属 Case、所属字段。
- **歧义（ambiguity）**：上下文不足以判定指代。**不猜**，登记下来由人裁决。
- **词间关系（relation）**：词条之间的有向边：上位于、下位于、整体、部分、近义、反义、相关。

## 领域规则（Given-When-Then）

### 词条与词面

- Given 一个概念 When 登记 Then 得到稳定标识；**显示名与标识分开**，
  改名不改标识（否则历史引用会断）
- Given 同一个概念 When 有多个叫法 Then 都登记为它的词面，并注明每个词面的**来历**
  （来自哪份文档、谁加的）
- Given 两个词面 When 指向同一个词条 Then 它们同义；
  **不要**再用「近义」关系去表达同一件事
- Given 一个词面 When 可能指多个概念 Then **不得**强行绑定一个；
  登记为多义，逐义项说明，并尽量补上能把它们分开的条件
- Given 一个词条 When 还没有任何词面 Then 允许（先有概念后有名字），
  但界面显示标识并说明「暂无中文名」——**不编名字**
- Given 一个词面 When 登记 Then 必须能回答它**凭什么**指这个词条（来自哪份文档的哪一段、
  或谁根据什么加的）——无来历的词面不得登记

### 条件指代

- Given 一个词面 When 在特定条件下固定指某个词条 Then 登记为**条件指代规则**。
  条件可以是：所在文档、所在 Case、邻近词、所属字段、旁的限定词
- Given 一段文本里出现一个多义词面 When 分析 Then 用条件指代规则判定；
  命中唯一规则时判定并**记录用了哪条规则**
- Given 多条规则同时命中且指向不同词条 Then 判为**歧义**，不猜
- Given 没有规则命中且该词面有多个义项 Then 判为歧义，不自动选一个
- Given 一条规则命中 When 记录 Then 必须留下「凭什么判」；
  无依据的判定不得写入
- Given 条件里写的是文档或 Case When 该文档/Case 不存在 Then 拒绝登记并指出位置
- Given 同一个词面 When 在不同 Case 里指不同词条 Then 用 Case 作为条件表达——
  这是**合法的**，不是冲突

### 歧义与裁决

- Given 上下文不足以判定指代 When 处理 Then 产出**歧义事项**
  （机制见 `decision.spec.md`，与数据抽取遇到的歧义是同一套机制）
- Given 一个歧义事项 When 产生 Then 必须携带：全部候选义项、上下文片段、所在段落，
  使人不打开原文也能判断
- Given 一个人 When 裁决 Then 记录选了哪个、凭什么、是谁；
  **agent 不能代替人拍板**（见 `agent.spec.md`）
- Given 一次裁决 When 记录 Then 它成为一条**条件指代规则**：
  下次遇到同样的上下文**直接判**，不得每次重新问人
- Given 已裁决的指代 When 上下文变了 Then 该判定标为「需复核」，不静默失效也不静默沿用
- Given 同一个歧义 When 又被遇到 Then 不重复产生事项，指向已有判定或已有待裁决事项
- Given 一个指代判定 When 被推翻 Then 记为新判定，旧判定保留——
  推翻是审计信息，「上次判成了什么」将来还会被问到

### 词间关系

- Given 两个词条 When 建立关系 Then 必须指明**种类与方向**：
  上位于 / 下位于、整体 / 部分、近义、反义、相关
- Given **同义**与**近义** When 判断 Then 严格区分：
  同义是「两个词面指同一个词条」；近义是「两个不同的词条意思接近」。
  混用会让「我们说的东西是一个」这句话失去意义
- Given 上位于/下位于、整体/部分 When 成环 Then **拒绝**——那意味着定义不成立
- Given 近义、反义、相关 When 成环 Then 允许
- Given 一个词条 When 打开 Then 能看到：词面、义项、关系、
  以及它出现在**哪些文档的哪些段落**

### 与文档、数据定义的连接

- Given 一份文档 When 分析 Then 命中的词面挂到该文档的段落上（见 `document.spec.md`）
- Given 一个词条 When 打开 Then 能看到它的全部出现位置，并能逐条跳到原文
- Given 一个数据定义里的字段 When 登记 Then 它的名字**挂到一个词条上**——
  字段名与「我们说的东西」是同一套指代，不得各搞一套
- Given 一个词条 When 改名 Then 只是新增或调整词面，**标识不变**，历史引用不受影响

### 合并与拆分

- Given 两个词条 When 被判定为同一件事 Then **合并**；
  被合并方的标识**保留为别名**，使旧引用仍然解析得到
- Given 一次合并 When 完成 Then 全部词面、关系、出现位置、字段挂载都转到合并后的词条
- Given 一个已被合并的词条 When 又被当作独立词条登记 Then 报出并提示
  「这可能是要拆分」，需人确认——不静默重建，也不静默拒绝
- Given 一次合并 When 需要撤销 Then 走拆分流程，且必须在界面上标明历史合并点

## 验收标准

- [ ] 词条有稳定标识，改名不改标识，历史引用不受影响
- [ ] 一个词条可有多个词面，每个词面注明来历
- [ ] 无来历的词面被拒绝登记
- [ ] 一个词面可对应多个义项，不被强行绑定到单个词条
- [ ] 词条没有词面时显示标识并说明「暂无中文名」，不编名字
- [ ] 条件指代规则可带条件（文档、Case、邻近词、字段）
- [ ] 条件命中唯一规则时判定并记录用了哪条规则
- [ ] 多条规则指向不同词条时判为歧义，不猜
- [ ] 无规则命中且义项多于一个时判为歧义
- [ ] 同一词面在不同 Case 里指不同词条时用 Case 条件表达，不算冲突
- [ ] 歧义事项携带全部候选与上下文片段，不打开原文也能判断
- [ ] 歧义裁决记录含选择、理由、裁决者，且裁决者是人
- [ ] 裁决后成为条件指代规则，同样上下文不再重复问人
- [ ] 同一歧义不重复产生事项
- [ ] 已裁决的判定在上下文变化后标为「需复核」
- [ ] 判定被推翻后新判定生效、旧判定保留
- [ ] 词间关系有种类与方向
- [ ] 同义与近义严格区分，不混用
- [ ] 上下位与整体部分关系成环时被拒绝，近义与相关允许成环
- [ ] 词条能看到它出现在哪些文档的哪些段落，并可跳转
- [ ] 数据定义里的字段名挂到词条上
- [ ] 合并保留被合并方的标识作为别名，旧引用仍解析得到
- [ ] 合并可撤销，且历史合并点在界面上可见

## 边界与异常

- 词面为空：拒绝
- 同一词面在同一条件下被两条规则指向不同词条：拒绝登记第二条并指出冲突
- 词面含空格、标点、大小写、全半角差异：匹配时归一，但**记录原始写法**
- 一个词条被合并后又作为独立词条登记：报出并提示可能是在拆分，需人确认
- 条件指代规则引用了不存在的文档或 Case：拒绝，指出位置
- 一个多义词面在上下文里两个义项都说得通，且条件规则都无法排除：判为歧义
- 一个词条没有任何文档命中：允许；界面说明「这个词还没有在任何文档里出现过」——
  这本身是信息（可能是编的词）
- 一个词面在词表里存在但文档里从未出现：同上，单独列出
- 项目没有任何词条：允许；界面说明后果——
  指代无法保证，Agent 的整理会各说各话
- 词表加载失败：文档与数据仍可读；依赖指代的判定全部标为「未能判定」，
  不得默认取第一个义项

## 前后端契约

`DictService`（作用域：项目）：

| 方法 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `List` | `q, limit` | `TermView[]` | 按显示名与词面搜索 |
| `Get` | `id` | `TermView` | 含词面、义项、关系、出现位置计数 |
| `Put` | `TermInput, by, reason` | `TermView` | 需人拍板 |
| `Merge` | `from, into, by, reason` | `TermView` | 被合并方标识保留为别名 |
| `Split` | `id, into, by, reason` | `TermView[]` | 撤销一次合并 |
| `Relate` | `from, to, kind, by, reason` | — | 成环时按种类判定是否拒绝 |
| `Unrelate` | `from, to, kind, by, reason` | — | 解除记录保留 |
| `Surfaces` | `id` | `Surface[]` | 词面与来历 |
| `Senses` | `surface` | `Sense[]` | 一个词面能指哪些词条 |
| `Rules` | `id` | `RuleView[]` | 该词条的条件指代规则 |
| `PutRule` | `RuleInput, by, reason` | `RuleView` | |
| `Resolve` | `surface, context` | `Resolution` | **试判**：给定上下文判它指哪个；不写库 |
| `Ambiguities` | — | `AmbiguityView[]` | 歧义事项（与 `decision.spec.md` 同一队列） |
| `Decide` | `id, sense, by, reason` | `AmbiguityView` | `by` 必须是人 |
| `Occurrences` | `id` | `HitView[]` | 出现在哪些文档的哪些段落 |

`TermView`：

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | string | 否 | 稳定标识 |
| `name` | string | 否 | 显示名；为空时界面显示标识并说明「暂无中文名」 |
| `note` | string | 否 | 说明 |
| `surfaces` | `Surface[]` | 否 | 至少一项才算可用 |
| `senses` | int | 否 | 该词条被多少个词面指到 |
| `relations` | `RelationView[]` | 否 | |
| `occurrences` | int | 否 | 在文档里出现多少处 |
| `ambiguous` | int | 否 | 其中多少处尚未判定 |
| `signedBy` | `ActorView \| null` | 是 | 拍板者 |
| `revision` | string | 否 | 词表版本标识 |

`Surface`：`{ text, kind, origin, note }`，
`kind` 为 `name`（正式名）/ `alias` / `abbr` / `foreign` / `legacy`（旧名）；
`origin` 说明来历（哪份文档的哪一段，或谁加的）。

`Sense`：`{ term, name, rules: int, hits: int }`
——这个词面指哪个词条、有几条规则能把它判到这里、实际命中多少处。

`RuleView`：`{ id, surface, term, when: string, note, decidedBy, at }`
——`when` 是条件的可读表述（如「在文档 Data:Skill/262_01 中」）。

`Resolution`：

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `status` | string | 否 | `resolved` / `ambiguous` / `unknown` |
| `statusText` | string | 否 | 中文说明 |
| `term` | string | 否 | 判定结果；未判定时为空串 |
| `why` | string | 否 | 凭什么判的：用了哪条规则，或为什么判不了 |
| `candidates` | `Sense[]` | 否 | 歧义时的全部候选 |

`AmbiguityView`：`{ id, kind, subject, candidates, context, docId, anchor, status, decidedBy, reason }`
——`kind` 为 `reference`（指代）/ `extraction`（抽取），见 `decision.spec.md`。

`HitView`：`{ docId, title, revision, anchor, text, status }`，
`status` 为 `resolved` / `ambiguous` / `overturned`。

约定：

- `Resolve` 是**只读试判**：界面可以拿它做即时预览，但它不产生判定记录；
  真正的判定发生在文档分析时
- 每个判定都必须带 `why`；`why` 为空的结果在服务层拒绝
- `Put` / `PutRule` / `Merge` / `Split` / `Relate` 都要求人的拍板与理由
- `Occurrences` 必须给到段落级并可跳转，否则「出现在哪些文档」只是个不好用的索引

## 待确认

1. 词面的匹配规则细节：空白、标点、大小写、全半角的归一策略与边界
2. 条件指代的 `when` 表达力上限（是否允许组合条件与否定条件）
3. 义项是否需要一个稳定的义项标识（当前用「词面 + 词条」隐含表达）
4. 词表是否需要导入/导出的标准格式（对接外部词典或既有术语表）
5. 一个词面的义项过多时的提示阈值
