# 备选方案：多解输出与取舍呈现

## 目的

方案输出不是单一最优解，而是**一组取舍不同、来源可辨、代价显式的备选**。

三个理由：

1. **建议类内容无法裁决**（见 `verification.spec.md`）——冲突应当被**呈现**，而不是被消除或自动择一。
2. **玩家偏好不同**——单一答案不可能同时对全图鉴党、斗技党、新区玩家成立。
3. **未声明偏好时，让用户在选择中暴露偏好，比先填问卷更省事。**

核心立场：**系统不替用户做取舍。** 它负责把取舍、代价、依据、不确定性摊开，让选择可见。

## 术语

- **方案（plan）**：一组可执行的行动，针对某个目标。
- **目标（objective）**：该方案在优化的东西（期望收益最大 / 资源消耗最少 / 时间最短 / 风险最小）。
- **代价（cost）**：执行该方案要付出的资源、时间与机会成本。**机会成本必须显式给出**。
- **支配（dominate）**：方案 A 在**所有**维度上都不劣于 B，且至少一个维度严格更优。
- **Pareto 最优集**：不被任何其他方案支配的方案集合。
- **方案分裂**：多个来源冲突时，各自成为独立方案。
- **方案合并**：多个来源一致时，合并为一个方案。
- **敏感性**：关键假设变化时，方案是否仍然成立。

## 领域规则（Given-When-Then）

### 由来源决定分裂还是合并

- Given 多个来源给出**冲突**的建议 When 生成方案 Then **各自成案**，不合并、不择一
- Given 多个**独立**来源给出一致建议 When 生成方案 Then 合并为一个方案，且可信度提升
- Given 多个**不独立**来源给出一致建议 When 生成方案 Then 合并，但可信度**不提升**
- Given 某来源的断言已被驳回 When 生成方案 Then 不得据其成案

> 独立性判定见 `verification.spec.md`。**三个互相转载的攻略不是一个方案，也不是三个独立证据。**

### 偏好缺失时给多解

- Given 玩家未声明玩法倾向 When 请求生成方案 Then **不得**生成「针对该玩家的单一方案」
- Given 玩家未声明玩法倾向 When 请求生成方案 Then **可以**生成备选集合，但每个备选必须**显式标注它假设了哪种偏好**
- Given 玩家在备选中做出选择 When 记录 Then 该选择可作为偏好声明的依据
- Given 系统从历史选择中推断出偏好 When 影响后续默认偏好 Then **必须显式确认**，不得静默改变

### 每个方案必须自证

- Given 一个方案 When 输出 Then 必须声明它优化的目标与遵守的约束
- Given 一个方案 When 输出 Then 必须显式给出代价：资源消耗、时间投入、**机会成本**
- Given 结果含随机因素 When 输出 Then 给出区间或期望，**不得只给单点值**
- Given 一个方案 When 输出 Then 必须给出它所依赖断言中**未核验的比例**
- Given 一个方案完全建立在未核验内容之上 When 输出 Then 允许，但必须置于显著位置说明

### 可比性与剪枝

- Given 多个方案 When 呈现 Then 必须能在**同一组维度**上对比
- Given 某方案被另一方案支配 When 生成 Then **应被剪枝**
- Given 两个方案在各维度上的差异低于阈值 When 生成 Then 合并，避免伪多样性
- Given 全部方案都被剪枝 When 生成 Then **报出互相冲突的约束**，不得返回空结果
- Given 最终只有一个方案 When 输出 Then 明确说明「未发现实质不同的备选」，**不得假装有多样性**

### 敏感性

- Given 方案依赖某个关键假设 When 输出 Then 必须说明该假设变化时方案是否失效
- Given 玩家补充了新事实（例如刚抽到某式神） When 重新生成 Then 受影响的方案被标记，而非静默替换

### 持久化与可信度

- Given 一个方案被生成 When 输出 Then **必须持久化**，记录其所依赖断言的标识与版本、所假设的偏好、代价、生成时间
- Given 一个已持久化的方案 When 重新查询 Then 必须能复现其**原始内容与原始依据**，不受后续数据变化影响
- Given 一个已持久化方案的依据发生变更（来源修订、断言被驳回、数据过期） When 系统检测到 Then 方案标记为「依据已变」，**不得静默沿用**
- Given 一个已持久化方案所依赖的断言被驳回 When 该方案被执行 Then **拒绝执行**并指出失效依据
- Given 一个方案 When 输出 Then 必须带**方案级核验状态**，其可信度**不得高于**其所依赖断言中的最低可信度
- Given 一个方案仅来自单一未核验来源 When 输出 Then 标记为未核验
- Given 一个方案来自多个**独立**来源一致 When 输出 Then 其可信度高于任一单一来源方案
- Given 两个方案被合并 When 记录 Then 被合并方案的历史记录保留，**不得删除**

### 选择与反馈

- Given 玩家选定一个方案 When 记录 Then 保留**选择理由**与时间，并一并持久化
- Given 方案被执行 When 记录结果 Then 该结果可作为调整相关来源可信度的依据之一
- Given 玩家长期选择某一类方案 When 生成新方案 Then 可据此调整呈现顺序，但**不得删除其他备选**

## 验收标准

- [ ] 冲突来源各自成案，系统不自动择一
- [ ] 独立多源一致时合并且可信度提升；不独立时合并但可信度不提升
- [ ] 已驳回断言不参与任何成案
- [ ] 未声明偏好时不产生单一方案，而是产生标注了各自偏好假设的备选集合
- [ ] 每个方案都声明目标、约束、代价（含机会成本）与未核验比例
- [ ] 含随机因素的结果以区间或期望呈现，不出现单点断言式结论
- [ ] 被支配的方案被剪枝
- [ ] 差异低于阈值的方案被合并
- [ ] 方案可并排对比
- [ ] 全部方案被剪枝时，输出的是冲突的约束清单而非空结果
- [ ] 仅有一个方案时明确说明未发现实质不同备选
- [ ] 关键假设失效时，受影响方案被标记
- [ ] 偏好推断需经显式确认才生效
- [ ] 玩家选定方案后，其他备选仍可访问
- [ ] 方案被持久化，重新查询能复现原始内容与原始依据
- [ ] 依据变更后方案被标记为「依据已变」，且不静默沿用
- [ ] 依据被驳回后，方案不可执行且指出失效依据
- [ ] 方案带方案级核验状态，且不高于其依赖断言的最低可信度
- [ ] 单一未核验来源产生的方案被标记为未核验
- [ ] 独立多源一致的方案，可信度高于单一来源方案
- [ ] 玩家选择与理由被持久化
- [ ] 方案合并后，被合并方案的历史记录仍可查

## 边界与异常

- 两个方案互为 Pareto 最优但难以区分：输出其差异维度，帮助选择，**不得随机择一**
- 方案数量超过上限：按某维度截断，并说明截断依据与被舍弃的方案特征
- 所有方案都依赖未核验内容：允许输出，但整组方案必须带统一警示
- 方案之间约束互斥（无法同时满足）：报出冲突约束，这是信息，不是错误
- 玩家声明的偏好与历史选择矛盾：并列呈现，询问以哪个为准，**不自动采信任一方**
- 某方案的依据在生成后失效（来源修订、被驳回）：方案转为「依据已变」，不得静默沿用
- 无可行方案（约束过紧）：报出哪条约束导致无解，并给出放宽哪条约束会带来什么
- 同一目标下两个方案资源需求相同但风险不同：视为不同方案（风险是独立维度）
- 方案持久化后其依据被删除：方案保留，依据引用标记为待处理（与 `player-profile.spec.md` 的引用规则一致）
- 持久化方案的依据包含已被驳回的断言：方案标记失效，且不得再被执行
- 重新生成的方案与历史方案结论相同但依据不同：视为不同方案版本，保留两者
- 方案依据的源已被删除且无副本：方案保留但依据标注「不可达」

## 前后端契约

**待定**，取决于对外接口形态。已确定的约束：

- 必须能**并排对比**多个方案的同一组维度
- 玩家必须**显式选择**，不得有默认选中项
- 每个方案的依据、代价、未核验比例都必须可被外部读取，而不只显示在界面上
- 已选方案与其他备选必须同时保留可访问

## 待确认

1. 备选数量的上限，以及超出时的截断维度
2. 「差异低于阈值即合并」的阈值由谁定：部署默认还是用户可调？
3. 玩家偏好的推断是否一律需要确认，还是仅在高影响场景需要
4. 方案的保留期限与清理策略（已确定持久化，但保留多久未定）
5. 方案可信度与其依赖断言最低可信度之间的绑定，是否允许人工上调？（倾向**不允许**——
   否则核验分级会被绕过）

## 附：与 `player-profile.spec.md` 的冲突及修正

`player-profile.spec.md` 原规则为：

> Given 玩家未声明玩法倾向 When 请求生成任何方案 Then **拒绝生成**

本 spec 要求「未声明偏好时输出多解，让用户在选择中暴露偏好」。二者需要调和，已在
`player-profile.spec.md` 中修正为：

> 未声明偏好时，**不得**生成「针对该玩家的单一方案」；**可以**生成备选集合，
> 但每个备选必须显式标注其假设的偏好，且玩家必须做出选择。

这是 SDD 流程的正常工作方式：**发现规格冲突时先改规格，再改实现。**
