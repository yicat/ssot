# 场景：项目内的一个用途

## 目的

定义**项目内的一个具体用途**。

- **项目**定义一个领域：阴阳师有哪些实体、数据从哪来、有哪些公共公式。
- **场景**定义**用这个领域回答一个具体问题**：斗技阵容分析、每日/每周任务、每月攒资源、备战活动、伤害计算器。

场景是「**缺什么**」的载体。它声明自己需要什么，系统据此报告缺什么——
把数据缺口从「事后发现」变成「事前可见」。

这也是把「模拟斗技需要哪些系统」这类问题变得可回答的机制：
不靠先验地画一张机制大图，而是**由场景声明它的 `requires`**。

## 术语

- **场景（scenario）**：项目内的一个用途，落在 `scenarios/<name>/` 下。
- **requires**：该场景需要哪些数据。缺失即不可运行。
- **输入声明（inputs）**：该场景读取个人档案的哪些字段。
- **偏好声明（preferences）**：该场景需要用户显式声明的选择。
- **输出（outputs）**：该场景产出的视角与方案。
- **可运行性（runnability）**：requires 是否全部满足。**不可运行 ≠ 出错。**

## 一、场景声明什么

| 声明 | 含义 | 例（斗技阵容分析） |
|---|---|---|
| `requires` | 需要哪些数据 | 式神属性、技能、御魂套装、版本平衡规则、当前 meta |
| `inputs` | 读个人档案的哪些字段 | 持有式神与技能等级、御魂库 |
| `preferences` | 需要用户声明什么 | 冲分还是娱乐 |
| `formulas` | 依赖哪些公式 | 速度线、控制命中判定、伤害估算 |
| `outputs` | 产出哪些视角/方案 | 阵容推荐、克制关系、我的缺口 |
| `version` | 场景自身的版本 | — |

`requires` 的每一项必须**可判定**：要么有对应数据，要么没有。
**不得声明无法判定的需求**（例如"游戏理解"）。

### 场景目录

```
scenarios/<name>/
├─ scenario.yml     声明：requires / inputs / preferences / outputs
├─ formulas/        场景私有公式
├─ views/           该场景的视角
└─ experience/      经验（场景级）
   ├─ entries/      经验条目（责任级别、推导链、适用条件）
   └─ sessions/     会话记录（= 依据／原件）
```

**经验挂在场景下**，不是项目级：它是围绕这个用途长期累积的**判断**，
而项目级承载的是上下文中立的**事实**（断言与派生断言）。详见 `experience.spec.md`。

## 二、三层：引擎 / 项目 / 场景

| 层 | 是什么 | 边界性质 |
|---|---|---|
| **引擎** | 机制：断言、准入、核验、迁移、计算、投影 | 全局统一 |
| **项目** | 一个领域：schema、数据源、单位表、公共公式 | **隔离边界**——项目间数据互不可见 |
| **场景** | 一个用途：requires、输入、输出 | **用途边界**——同项目内的断言**共享** |

**关键区别：场景不是隔离边界。** 同一项目下所有场景读同一批断言；
场景只组织「读什么、算什么、产出什么」。

## 领域规则（Given-When-Then）

### 完整性检查

- Given 一个场景 When 检查完整性 Then 逐项报告其 `requires` 中哪些已满足、哪些缺失
- Given 某场景的 `requires` 存在缺失 When 运行该场景 Then **拒绝运行**并列出缺失项，
  **不得静默降级**，也不得用不完整数据产出方案
- Given `requires` 中的某项依赖外部源而该源暂不可用 When 检查 Then 标记为
  **「不可用」而不是「缺失」**——区分「这个数据不存在」与「暂时取不到」
- Given 场景的 `requires` 全部满足 When 检查 Then 标记为**可运行**

### 依赖的判定

- Given 场景依赖某个公式 When 该公式不存在或算例未通过 Then 该场景标记为不可运行
- Given 场景依赖某些断言 When 这些断言全部未核验 Then 场景**可运行**，
  但输出必须标注未核验比例（见 `verification.spec.md`）
- Given 场景依赖的断言被驳回 When 检查 Then 该场景标记为不可运行并指出失效依赖

### 输入

- Given 场景声明了 `inputs` When 个人档案缺少其中某项 Then 报告缺失，
  并说明该场景需要用户提供什么
- Given 场景声明了 `preferences` 而用户未声明 When 运行 Then 按
  `alternatives.spec.md` 产出多个备选，每个标注其假设的偏好
- Given 场景读取了未在 `inputs` 中声明的档案字段 When 检查 Then **拒绝**，
  防止场景越权读取用户数据

### 输出

- Given 一个场景 When 运行 Then 只产出其 `outputs` 中声明的视角与方案
- Given 场景产出方案 When 输出 Then 必须携带该场景的 `requires` 满足情况与未核验比例

### 场景之间

- Given 同一项目下的多个场景 When 运行 Then 共享同一批断言，**互不隔离**
- Given 场景的**中间结果** When 另一个场景需要同样的值 Then **不得共享**；
  应提示该结果可能上下文中立，宜提升为派生断言（见 `derivation.spec.md`）
- Given 两个场景定义了同名公式但内容不同 When 检查 Then 报冲突，**不得其中一个静默生效**
- Given 场景需要使用项目级公式 When 引用 Then 允许；场景私有公式优先于项目级同名公式**但必须显式声明覆盖**

### 生命周期

- Given 一个场景 When 启用 Then 参与完整性检查
- Given 一个场景 When 禁用 Then 不参与检查，其历史方案仍可访问
- Given 场景的 `requires` 未被满足 When 展示 Then 标记为「不可运行」而非「错误」
- Given 场景定义变更 When 应用 Then 走 `migration.spec.md` 的流程

## 验收标准

- [ ] 完整性检查逐项报告 `requires` 的满足情况
- [ ] `requires` 缺失时拒绝运行并列出缺失项，不降级
- [ ] 区分「不可用」（源暂不可达）与「缺失」（数据不存在）
- [ ] 依赖的公式缺失或算例未通过时场景不可运行
- [ ] 依赖的断言全部未核验时场景仍可运行，但输出标注未核验比例
- [ ] 依赖被驳回断言时场景不可运行并指出失效依赖
- [ ] 个人档案缺少 `inputs` 时报告需要用户提供什么
- [ ] 未声明偏好时产出多备选并标注各自假设
- [ ] 场景读取未声明的档案字段时被拒绝
- [ ] 场景只产出 `outputs` 中声明的输出
- [ ] 方案携带 requires 满足情况与未核验比例
- [ ] 同项目内场景共享断言
- [ ] 两个场景的同名公式冲突被报出
- [ ] 场景私有公式覆盖项目级同名公式时必须显式声明
- [ ] 禁用场景不参与检查但历史方案仍可访问
- [ ] 不可运行的场景被标记为「不可运行」而非「错误」

## 边界与异常

- 场景名为空或与同项目内其他场景重复：拒绝
- `requires` 为空：允许，但标记为「不依赖数据」——这类场景只能是纯计算或纯展示
- `requires` 中出现无法判定的项（如"游戏理解"）：拒绝加载并说明原因
- `outputs` 为空：允许，但场景无产出意义，标注提示
- 场景依赖另一个场景的输出：允许，但必须声明依赖且检测循环
- `inputs` 引用了项目中不存在的档案字段：拒绝加载
- 场景的公式引用了不存在的字段：拒绝加载并指出位置
- 场景运行中途数据源失效：中止并报告，已产出的部分**不得作为方案保存**
- 项目被删除时场景一并处理（见 `project.spec.md`）
- 场景的 requires 长期不可满足：允许保留，但应能查询「哪些场景因缺数据长期不可运行」

## 前后端契约

**待定**，取决于对外接口形态。已确定的约束：

- 每个场景的**可运行性与缺失项**必须可被外部查询——这是「缺什么」的对外表达
- 场景必须能**独立启用/禁用**，且这是可脚本化的操作
- 场景的输出必须能追溯到它依赖的断言与公式

## 待确认

1. 场景能否调用另一个场景的输出（当前设计为**允许但需声明并检测循环**）
2. 场景私有公式与项目级公式的优先级规则细节
3. 是否需要「场景模板」——从一个场景派生另一个
4. 场景的 `requires` 是否细到字段级，还是只到实体级
5. 一个场景能否有多种运行模式（例如"快速估算"与"精确计算"）
