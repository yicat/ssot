# 三个案例的需求拆解

> 目的：用三个真实案例反推「需要哪些数据、我们有没有、还缺什么」。
> 方法：**从需要的输入反推**，而不是先验地画机制大图（见 `semantics-design.md` 第六节）。
> 数据现状基于实测：已同步 423 个页面（`Data` 命名空间）与关键词扫描结果。

## 案例 1：每月攒勾玉 / 蓝票 / 黑蛋

**用户想问**：按我的玩法和投入，这个月能攒到多少？够不够达成目标？

### 需要的共享事实

| 需求 | 说明 |
|---|---|
| 资源定义 | 有哪些资源、是否有上限、是否可交易 |
| 产出源 | 每个来源的名称、单次产出、**周期**（每日/每周/每月/活动）、前置条件 |
| 消耗源 | 召唤消耗、技能升级消耗、其他 |
| 兑换关系 | 资源之间能否互换、商店价格 |
| 概率 | 抽卡出货概率（决定「期望需要多少抽」） |

注意：勾玉与御行达摩（黑蛋）是**两套独立经济**，来源完全不同，不能混在一个"存款"里算。

### 需要的个人输入

- **状态**：当前库存、每日可投入、日常完成情况
- **偏好/目标**：目标是什么（下个 UP 池抽多少次 / 某式神满技能）、玩法倾向

### 需要的规则

资源流图遍历 → 周期性求和 → 期望值 → 差距与可行性

### 现状

| 关键词 | 实测结果 |
|---|---|
| 黑蛋 | **0 次**（社区叫法，wiki 无此词） |
| 蓝票 | **0 次**（同上） |
| 御行达摩 | 2 文件 / 3 次（wiki 正式叫法，也几乎没有） |
| 勾玉 | 22 文件 / 80 次（**全在式神传记叙事里**） |

→ **所需数据全部缺失。**

## 案例 2：备战超鬼王（2025）

**用户想问**：我要练什么、备什么、来得及吗？

### 需要的共享事实

| 需求 | 性质 |
|---|---|
| 活动定义：时间、玩法机制、阶段、要求、奖励 | 客观 |
| **推荐配置**：推荐式神、御魂、配置门槛 | **建议（社区产出）** |
| 该年份的具体规则（与往年差异） | 客观 + 版本 |

### 需要的个人输入

- **状态**：持有式神及技能等级、御魂库
- **偏好**：能投入多少时间与体力、目标是通关还是高分
- **时间**：距活动开始还剩多久

### 需要的规则

需求与状态的差距 → 投入产出估计（练满一个式神要多少达摩/时间）→ 排期可行性

### 现状

`超鬼王` 在 423 个已同步页面中**只出现 1 次**，且是在 `Data_Skin.json` 里被顺带提及。

→ **活动数据与推荐配置全部缺失**，且推荐配置**天然不在 wiki 客观层**。

## 案例 3：最近斗技环境 + 给出阵容

**用户想问**：现在斗技什么强？我该用什么阵容？

### 需要的共享事实

| 需求 | 性质 |
|---|---|
| **meta**：当前版本强势式神/御魂/套路、使用率 | **建议 + 强时效** |
| 克制关系 | 半客观（社区 + 规则推导） |
| 斗技专属规则：平衡限制（某些式神/御魂受限） | 客观 + 版本 |
| 版本标识 | 客观 |

### 需要的个人输入

- **状态**：持有式神与技能等级、御魂质量（速度线、暴击等）
- **偏好**：冲分还是娱乐、可接受的肝度

### 需要的规则

约束下求解：我有什么 × 当前 meta × 我的偏好

### 现状

`斗技` 出现 **104 文件 / 109 次**，但**没有一条是斗技数据**——全部来自式神传记文本
（例如传记解锁条件里提到斗技）。

→ 这是「关键词命中 ≠ 数据可得」的直接证据。**所需数据全部缺失。**

## 汇总：需要补的数据源

| 数据 | 性质 | 可能来源 | 是否在 wiki |
|---|---|---|---|
| 资源产出/消耗/兑换 | 客观 | wiki 主命名空间页面 | 待验证 |
| 日常/周常/月常任务表 | 客观 | 同上 | 待验证 |
| 活动定义与排期 | 客观 | 官方公告 / wiki 活动页 | 部分 |
| 抽卡概率 | 客观 | 官方公示 | 待验证 |
| **备战推荐配置** | **建议** | 社区攻略 | ❌ 天然不在 |
| **斗技 meta** | **建议** | 社区 / 统计站 | ❌ 天然不在 |
| 克制关系 | 半客观 | 社区 + 规则推导 | ❌ |
| **版本信息** | 客观 | 官方公告 | ❌ **已确认 wiki 无** |

## 四个结论

1. **三个案例都同时需要「客观事实」与「社区建议」**，而后者**不在 wiki 客观数据层**。
   → 印证 `semantics-design.md` 的结论：SSOT 必须是**唯一权威整合点**，而非唯一数据源。

2. **版本信息是共同的前置依赖**，且已确认 wiki 的 schema 里没有版本字段。
   → **必须先解决版本源**，否则案例 2、3 的时效性无从谈起。

3. **案例 1 最容易先做**：最接近「纯客观数据 + 个人状态」，几乎不需要社区建议。

4. **案例 3 最难**：几乎完全依赖社区建议与快速过期的 meta。

**建议实施顺序：案例 1 → 案例 2 → 案例 3。**
