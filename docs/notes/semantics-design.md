# 语义模型设计：指代、来源、时效、关系、可扩展性

> 回答六个问题：指代正确、规则可扩展、不漏、跨渠道冲突、内容过期、关系关联。
> 本文是**设计回答**，尚未成为规范；确认后再落成 `docs/specs/` 下的 spec。
> 所有例子都取自实测数据（`tools/wiki/`、`.huiji/raw/`）。

## 零、共同的根：从「实体 + 字段」升级为「带限定条件的断言」

现在的模型假设一条事实 = 某实体的某个字段值。这个假设在阴阳师这种**持续打补丁的实时服务游戏**里不成立。

推荐的基础单元：

```
断言 Assertion
├─ subject      实体稳定 ID（不是名字）
├─ predicate    属性名或关系名
├─ value        值，或指向另一个实体的 ID
├─ qualifiers   限定条件
│   ├─ 适用版本 / 时间区间
│   ├─ 场景（斗技 / PvE / 特定副本）
│   └─ 触发条件（"当目标带有减速时…"）
├─ source       来源 + 层级（官方 / 半官方 / 社区 / 实测）
├─ provenance   原文锚点 + revid + 时间戳
├─ confidence   L1 直引 / L2 结构化 / L3 推导 / L4 推断
└─ status       已核验 / 待核验 / 冲突 / 已过期 / 已知未知
```

**这个单元本身就是对六个问题的统一回答**——每个字段对应一个问题：

| 字段 | 解决的问题 |
|---|---|
| `subject` 稳定 ID + 别名表 | Q1 指代 |
| `predicate` / `qualifiers` 是数据，机制原语才是代码 | Q2 可扩展 |
| `status` 的「已知未知」+ 覆盖基线 | Q3 不漏 |
| `source` + 冲突并存 + 裁决记录 | Q4 跨渠道 |
| `qualifiers` 的时间/版本 + `status` 的过期 | Q5 时效 |
| `predicate` 构成机制图，视角声明所需 predicate | Q6 关系 |

## 一、Q1 指代正确

### 三个不同的毛病，别混为一谈

| 毛病 | 例子 | 性质 |
|---|---|---|
| **别名** | 同一个式神：官方名「不相狐禅」/ 玩家叫「葛根」「二舅」「小舅」 | 多对一，可枚举 |
| **歧义** | 「鬼火」既是资源，也可能是某个技能的产物 | 一对多，需消歧 |
| **条件性** | 同一 buff 在不同条件下效果不同 | **不是指代问题** |

### 设计

1. **实体用不可变 ID，绝不用名字做键**。我们已有基础：wiki 的 `pageid`、`Data:Character/<id>.json` 的 `id`。
2. **别名表是数据，不是代码**。而且**这个数据 wiki 已经给了**——实测：
   ```json
   {"id":604,"name":"不相狐禅","nickname":["葛根","二舅","小舅"]}
   ```
   需要扩展的是：别名要带**来源与适用范围**（社区叫法在官方语境下不该出现）。
3. **无法唯一确定时必须报歧义，禁止猜**。这是硬规则：宁可回答"这里指哪个？"，也不给一个可能错的答案。

### 关键澄清：条件性不是指代问题

「同一个指代在不同条件下有不同效果」——这不是"指代没搞清"，而是**我们把效果错建模成了实体的属性**。

正确做法：**效果是带 `qualifiers` 的断言**。

```
subject:   buff:2622_1
predicate: 效果
value:     提升攻击
qualifiers: { 触发条件: "自身总攻击为友方非召唤物中最高时" }
```

（这条来自真实数据：姑获鸟「协战」的描述里就有这个条件。）

所以 Q1 的正确回答是：**指代要唯一，效果要带条件**——这是两件事。

## 二、Q2 规则可扩展性（鬼火从一种变成多种）

### 把三类东西分开，可扩展性才有来源

| 类别 | 例子 | 放哪 | 扩展方式 |
|---|---|---|---|
| **术语 / 实例** | 鬼火、鬼火上限、某式神的独立鬼火池 | 数据 | 自由新增，不改代码 |
| **机制原语** | 消耗资源、资源上限、回合开始回复、行动条推进 | 代码（元模型） | 需要版本化的元模型升级 |
| **具体规则** | "鬼火上限为 8，回合开始 +3" | 声明式规则 | 引用机制原语，可配置 |

**可扩展性 = 尽量把东西下沉到"数据"，只把真正无法避免的原语留在"代码"，并且元模型自己也要能版本化升级。**

### 但必须留逃生舱：未建模 ≠ 丢弃

当 wiki 出现元模型表达不了的机制（这一定会发生），系统**不得拒绝或丢弃**，而应：

```
status: 未建模但已记录
```

先原样保存原文 + 锚点，标记为待建模。**漏掉一条信息，比暂时无法计算它严重得多**（Q3 同理）。

实测支撑：wiki 自己就是这个思路——`"_hjschema":"Character"` 是类型标记；`Data:SkillBuffs.json` 已经有 **1126 条 buff**，且 `SkillTips` 是一大块自由文本，说明机制确实在持续增长。

### 元模型升级的代价要可控

新增一个机制原语 → 需要：新原语 + 迁移脚本 + 历史断言的重解释规则。
**所以原语要尽量少、尽量正交**。宁可用"资源"这一个原语覆盖鬼火/妖气/其他，也不要为每种资源加一个原语。

## 三、Q3 保证不漏

### 必须诚实：有一部分原理上无法从 wiki 保证

分两种"漏"：

| 类型 | 能否保证 | 手段 |
|---|---|---|
| 结构化字段的漏 | ✅ 能 | 穷尽性检查（已有）+ 字段覆盖率（已有） |
| **玩家试出来、wiki 没写的机制** | ❌ **单源无法保证** | 只能靠多源汇入 + 显式登记"已知未知" |

### 设计

1. **覆盖基线**：对可枚举集合做三方对齐。已有实现（`verify.mjs` 检查 `CharacterIndex` / `Attribute` / `Character` 文件）。
2. **「已知未知」是一等状态**。留空 ≠ 未知。必须能区分：
   - 「这个式神没有这个字段」（不适用）
   - 「有这个字段但我们还不知道」（已知未知）
   - 「抓取时缺失」（可能是漏）
3. **多源汇入，一个认定**。SSOT 不是"只有一个数据源"，而是"**唯一权威整合点**"：
   ```
   wiki（官方口径）  ┐
   社区攻略          ├─→ 整合 → 每条带 source 与冲突标记 → 一个认定
   实战/模拟验证     ┘
   ```
4. **可发现性**：源页面 revid 变化 → 该页面产出的断言全部标记"待重核验"（我们已有 revid，机制现成）。

## 四、Q4 不同渠道同一指代完全不一样

官方描述与玩家实测经常冲突，而且**两边都可能错**——官方文案有笔误，玩家结论有以讹传讹。

### 设计：并存 + 冲突显式 + 裁决留痕

1. **不合并冲突断言**。两条都存，各自带 `source`。
2. **冲突不是错误，是待裁决状态**。`status: 冲突`。
3. **裁决记录 (adjudication) 是数据**，不是代码里的 if：
   ```
   裁决: assertion#A 与 #B 冲突
   依据: 实测样本 / 官方公告 2026-xx-xx
   判定: 采信 #A
   裁决人/时间: …
   ```
4. **「用哪个源」是视角的属性，不是数据的属性**：
   - 伤害计算类视角 → 优先实测
   - 文本展示类视角 → 优先官方
   同一份数据，不同视角取不同策略。

### 实测支撑

我们已经在数据里见过同事实两源的雏形：

| 源 | 形式 |
|---|---|
| `Data:Attribute.json` | `{"atk":3082,"cri":0.5}` 扁平、小数 |
| `Data:Character/262.json` | `{"atk":{"grade":"S","value":3082}}` 嵌套、百分数、带评级 |

两者**数值一致但量纲与结构不同**。现在需要的是：**万一它们不一致，系统怎么办**——答案是并存 + 报冲突，而不是"后写的覆盖先写的"。

## 五、Q5 内容过期

### 设计：一切断言带时效，过期不等于删除

1. **失效不删**：老攻略、历史对局、旧版本结论仍然有查询价值，只是不进默认视图。
2. **`qualifiers` 带版本区间**：`valid_from` / `valid_until`。查询必须带"当前版本"上下文。
3. **陈旧度指标**：每条断言记录 `last_verified_at` 与来源 `revid`。可问"哪些数据超过 N 天未核验"。
4. **重核验触发**：源页面 revid 变化 → 相关断言标记待核验。

### 一个真实缺口

我们检查过 `Data:Character.schema` 的字段清单：`id / name / cv / year / date / gender / grade / introduction / stats / zhuanji / huijuan / skills / document`。

**没有任何"版本"字段**。wiki 只记录 `year`（上线年份）和 `date`（实装日期）。

→ **版本信息必须从别处获取**（官方更新公告），这是当前未解决的依赖。
→ 在拿到版本源之前，只能退化为**按 `revid` + 时间戳做时效管理**，精度不如版本号。

### 已实测到的陈旧不均

同一批数据里，各页面的 revid 与时间相差很大：

```
Data:Character/262.json       revid=8053   2026-08-23
Data:CharacterIndex.json      revid=9939   2026-09-11
Data:Character.schema         revid=816    2026-07-20
```

→ **schema 比数据旧了两个月**，这本身就是"schema 漂移"（`tags`/`Voice` 未声明）的成因。

## 六、Q6 关系怎么关联（模拟斗技涉及哪些系统）

### 诚实回答：现在不知道

我们的数据里**没有一张"机制依赖图"**。所以"模拟斗技涉及哪些系统"这个问题，当前无法回答。

但可以设计出来，而且有个更可靠的做法。

### 做法：从「需要的输入」反推，而不是先验画大图

不要去画一张包罗万象的机制图谱（那会变成无人维护的文档）。而是**让视角声明它需要什么**：

```yaml
# 视角：斗技模拟
view: pvp-simulation
requires:
  - 双方阵容（式神 + 等级 + 御魂配置）
  - 行动条与出手顺序规则
  - 伤害计算规则
  - 控制命中判定规则（效果命中 / 效果抵抗）
  - 治疗与护盾规则
  - 鬼火/资源规则
  - 版本平衡规则（斗技专属限制）
```

**于是"涉及哪些系统"= `requires` 列表，而"缺什么"立刻可见**：
缺哪一项的数据，就跑不了这个视角，且**明确知道缺的是哪一项**。

这比先验大图的三个好处：
1. 可验证——每一项要么有数据要么没有
2. 自维护——视角变了，需求列表跟着变
3. 直接变成完整性检查——"要跑斗技模拟，还缺控制命中规则"

### 机制图仍会有，但是**推导出来的**，不是手画的

从技能/御魂描述里抽取关键词（"行动条""无视防御""效果命中""鬼火"），关联到机制节点。
实测可行性：`Data:SkillBuffs.json` 里 **445 处"伤害"、133 处"速度"、101 处"暴击"**，
`Data:SkillTips.json` 里 89 处"伤害"——**关键词关联是有语料基础的**。

但它产出的是**候选关系**，需要人工确认，仍是 L2/L4 级断言。

## 七、这套设计对现有 spec 的影响

`docs/specs/core.spec.md` 写于实测之前，前提已被推翻多处。至少需要补：

1. **断言模型**取代"实体+字段"（本文第零节）
2. **来源分级 + 冲突 + 裁决**（Q4）
3. **时效与失效**（Q5）
4. **别名表**与**歧义必须报错**（Q1）
5. **「已知未知」与「未建模但已记录」**两个状态（Q2/Q3）
6. **视角的 `requires` 声明**（Q6）
7. **量纲归一**（跨源比对前必做，已实测）

## 八、原理上受限、必须向用户明说的三件事

1. **单靠 wiki 无法保证"不漏"**——玩家试出来的机制不在 wiki 里。系统只能保证"不漏掉已知的"，并显式暴露"未知"。
2. **冲突可能永远无法自动裁决**——有些官方与社区的矛盾没有权威答案。系统能做的是**把它标出来**，而不是替用户选。
3. **版本信息当前无源**——在没有版本数据源之前，时效管理只能退化到 revid + 时间戳。
