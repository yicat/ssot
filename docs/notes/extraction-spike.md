# 抽取实测：3 篇文档跑一次（格式 / 消耗 / 耗时）

日期：2026-09-17。目的：在决定「整库抽取实体关系」之前，先量清**格式能不能稳定产出**、
**一次要花多少 token**、**多久**。结论：格式完全可用，但**消耗与耗时的外推要先解决两件事**
（批量、受限工具集），否则整库跑不划算。

## 怎么跑的

```powershell
# 一次性任务（dsh-headless），带上我们的 MCP overlay
$env:ELECTRON_RUN_AS_NODE=1; $env:DSH_HOME="$env:APPDATA\dsh-desktop\harness"
$env:SSOT_MCP_BIN=<仓库>\bin\ssot-cli.exe; $env:SSOT_MCP_VAULT=<vault>
& "…\DSH Desktop.exe" --expose-internals "…\harness-node-entry.mjs" `
  "…\node_modules\@deepseek-ai\dsh\lib\bin.js" --profile headless --patch .dsh\mcp.patch.yml "<任务文本>"
```

- `headless` profile 是**本轮新建**的（`dsh-base` + `dsh-headless`），建法与 `ssot-agent` 同：
  `~/.dsh/profiles/headless` 与 `%APPDATA%\dsh-desktop\harness\profiles\headless` 各一份。
- 任务：用 `mcp__ssot__file_read` 读 `raw/式神/{天邪鬼青,盗墓小鬼,寄生魂}.md`（各 3KB 上下），
  按 LightRAG 的字段输出一个 JSON（实体 name/type/description + 关系 source/target/keywords/description，
  每条带 `doc` + `line`）。
- ⚠️ **MCP 在 headless 里也走通了**：日志里有 `initialize 客户端=dsh-mcp-client` +
  `tools/list 被调用，返回 9 个工具`，说明 overlay 这条路与 ACP 那条是等价的。

## 结果

**格式**：完全可用。**12 个实体 / 9 条关系**，字段一个不缺，**12/12 都带合法文件行号**，
`doc` 是相对路径，description ≤40 字，keywords 是「技能/伤害」「CV/配音」这类高层词。
实体类型给的是「式神 / 技能」这种——**类型词表要我们自己定**（它默认只有 `Other` 兜底）。

**消耗与耗时**（从会话投影缓存 `storages/session_projcache/…json` 里的 `tokenUsage` 读的，不是估的）：

| 指标 | 数值 |
|---|---|
| 耗时 | **75 秒**（3 篇，一次任务） |
| 输入 · 未命中缓存 | 16,257 |
| 输入 · 命中缓存 | 38,400 |
| **输入合计** | **54,657** |
| **输出** | **13,327** |
| 单次调用的固定开销 | system 1,174 + **工具定义 7,863** + 消息 12,539 ≈ **21.5k** |

## 由此得到的三条结论（要做整库之前必须解决）

1. **输出里大头是推理**：3 篇文档产出 21 条实体/关系，却花了 13,327 输出 token
   ——CLI 打印的 `dsh: reasoning:` 说明推理也计进输出。想省钱就得**关/降推理**或换更快模型。
2. **⚠️ 绝不能「一块一次调用」**：单次调用的固定开销 ~21.5k（其中工具定义 7,863）。
   按块抽（8,667 块）≈ 8667 × 21.5k ≈ **1.9 亿输入 token**，纯浪费。
   **必须把多块/多篇合进一次调用**（比如一次 20 块 → 434 次调用 ≈ 9.3M 固定开销 + 正文）。
3. **工具集要收紧**：这次用的是 `dsh-base` 全套工具 + 我们的 9 个 MCP 工具，
   工具定义就 7,863 token/次。生产上应当用 `ssot-agent`（已禁用 pwsh/fs 那批），
   每次能省下几千 token——**这也顺便让抽取必须走能力层**。

## 外推（按本次实测，粗算，别当承诺）

- **按篇抽**：每篇 ≈ 18.2k 输入 / 4.4k 输出 → demo 的 410 篇 ≈ **7.5M 输入 / 1.8M 输出**，
  单机单线程耗时 ≈ **2.8 小时**（75 秒 × 410 / 3）。
- 并行跑多个任务能压时间，但**token 量不变**；想压 token 只能靠上面第 1、2 条。

## 关掉推理的 A/B（同一任务、3 篇、各跑一次）

旋钮：**DeepSeek 适配器只接受 `reasoningEffort ∈ {off, low, high, max}`，`off` 落成 wire 上的
`thinking: disabled`**（`dsh-llm-deepseek` 的 `reasoningEffort()` 与 resolve 处）。
落到 profile 上就是给 `agent-default-model` 那一行加 `reasoningEffort: off`——
仓库里有现成的 overlay：`.dsh/extraction.patch.yml`（与 `.dsh/mcp.patch.yml` 一起 `--patch`）。

| | run1（推理默认·全套工具） | run2（`off`） | **run3（`off` + 收工具集）** |
|---|---|---|---|
| 输入 · 未命中 / 缓存命中 | 16,257 / 38,400 | 3,554 / 25,344 | 13,314 / 9,984 |
| **输入合计** | 54,657 | 28,898（−47%） | **23,298（−57%）** |
| **输出** | 13,327 | 11,975（−10%） | **6,577（−51%）** |
| **耗时** | 75.0 s | 43.9 s（−41%） | **25.8 s（−66%）** |
| 工具定义 token | 7,863 | 7,863 | **5,220** |
| 实体 / 关系 | 12 / 9 | 11 / 8 | 11 / 8 |
| 坏行号 | 0 | 0 | 0 |

run3 = `--profile headless --patch .dsh/mcp.patch.yml --patch .dsh/extraction.patch.yml`
（后者把 pwsh/bash/fs/str-replace-editor 一并关掉，见 `.dsh/extraction.patch.yml`）。
**run1 → run3：输入 −57%、输出 −51%、耗时 −66%，格式与行号质量不变。**

**校准后的外推**：每篇 ≈ 7.8k 输入 / 2.2k 输出（= 23,298/3、6,577/3）→
demo 410 篇 ≈ **3.2M 输入 / 0.9M 输出**、单机单线程 ≈ **59 分钟**（25.8 s × 410/3）。

**怎么读**：
- 省得最多的是**输入**（−47%）——因为推理文本会进对话历史，之后每次调用都要重发一遍；
  关掉它就等于掐掉了这份复利。时间也跟着降 41%。
- 输出只降 10%：run2 的**最后一次调用**输出了 11,806 token（run1 是 3,679）——
  推理从 reasoning 通道消失后，有一部分"想"落到了正文里。净效果仍是省。
- ⚠️ **推理没有清零**（还剩 2 段），所以「`thinking: disabled` 是否真的生效」**没被证实**：
  有可能适配器照发了但模型仍回 `reasoning_content`，也有可能是 CLI 把某种 content 块标成
  reasoning。要settle得看 wire 层的请求/响应（**没做**）。
- **质量对比只到「格式没坏」这一层**（11/8 vs 12/9 条、坏行号都是 0）：
  单次、3 篇、每臂一次，**不能据此说质量没退化**，那要正经评测。

## 接生产时撞上的第一堵墙：**命令行长度**（2026-09-18）

要把「一次多块」落成代码，先得解决**提示词怎么送进去**：

- `dsh` 的 launcher（`node_modules/@deepseek-ai/dsh/lib/bin.js`）只认自己的旗标
  （`--profile` / `--patch` / `--dump-config`），**后面的 token 原样交给被启动的 app**；
  例子就是 `dsh --profile headless "run the tests"`——**任务文本是命令行参数**，
  没看到 stdin 或 `--prompt-file` 这类入口。
- Windows 的命令行上限是 **32,767 个字符**。我们的提示词除了块正文，还有固定的格式说明
  （~0.8k 字符）与每块的 doc/行号行；2000 token 的块正文≈2k 字符 →
  **一次只放得下 5～6 块**，而 `derived.spec.md` §三.1 明确要求「必须多块合一次」
  （按 20 块/次算是 434 次调用；按 6 块/次就是 ~1,250 次，固定开销白花一倍多）。

**所以抽取这条路要走 ACP，不走 headless one-shot**：ACP 把提示词放在**协议消息**里
（`session/prompt` 的 JSON 走 stdio），没有命令行长度这回事；本仓库已经有这条链
（`internal/infrastructure/acp` + `agentapp` + 界面上的会话），不需要新造。
代价是工具定义还是会带上（run3 实测 5,220 token/次），但这是**已知且有数**的开销。

⚠️ 这也意味着：上面 run3 的 token 数字是**用 headless 量的**，换成 ACP 后
固定开销会变（可能更低，因为不需要任务文本另起进程），**要重测**——别拿 headless 的数当 ACP 的承诺。

## P3 生产实测：走 ACP 的第一次真跑（2026-09-18）

`ssot vault extract`（新命令）走 ACP 发提示词，不传 MCP（正文已经在提示词里），
关推理 + 收工具集靠 `.dsh/extraction.patch.yml`（`SSOT_EXTRACTION_PATCH` 指路）。

**跑通了**：后端 `deepseek-harness-acp`，会话 cwd = vault 根，0 权限提示（抽取不用工具）。

| 跑法 | 块数（正文） | 一次调用的上下文 `used` | 产出 | 用时 |
|---|---|---|---|---|
| 4 批 × 2 块 | 每批 189～479 字 | 13,065 / 14,810 / 13,482 / 14,538 | 44 实体 / 38 关系 / **0 丢弃** | 60.4 秒 |
| 1 批 × 8 块 | 1,589 字 | **21,240** | 42 实体 / 25 关系 / **0 丢弃** | 32.0 秒 |

**读数**（`usage_update` 原样是 `{"used":N,"size":1000000}`——它给的是**上下文占用**，
不是账单；`size` 是 100 万窗口）：

- **固定开销 ≈ 13k token/次调用**：2 块一次就 13～15k，而正文才 200～480 字。
  8 块一次 21.2k → 每块边际 ≈1.2k。**所以批越大越省**——这印证了 spec §三.1
  「不许一块一次调用」，而且比当时估的还狠。
- ⚠️ **13k 比 spike 里 headless 的固定开销（工具 5,220 + system 1,174）高出一倍多**，
  原因没查（挂的插件更多？skills 目录？）——`OPEN.md` #25。**先别拿 spike 的 3.2M 外推当承诺。**
- **格式与溯源质量**：实体类型收敛到我们的词表（机制/技能/数值/…），描述像样的摘要，
  关系带 keywords；**所有行号都落在块区间内**（0 条需要退回、0 条被丢）。
  这是「格式没坏」级别的结论，**不是质量评测**（要看 20 篇 + 人工抽查）。

## P3 第四轮：提示词按坏例加固 + 成本探针的发现（2026-09-18）

**提示词加固**（`vextract/prompt.go`，测试里钉住了这几条）：把上一轮真跑里出现的坏例写进提示词——
**文件名/表名/路径**（`增益减益.csv`）、**命令与用法示例里的词**（`ssot vault`、`--patch`）、
章节序号与年份数字、空占位（`无`/`待定`）都**不算实体**；并且要求「尽量用具体类型，
**Other 太多等于没分类**」。

**成本探针撞的墙**：想拿 `--profile headless` 对比固定开销（spike 的数字是 headless 量的），
结果**握手就失败**：`acp: 后端连接已关闭`。原因不难理解——`headless` 是**一次性任务** profile
（`dsh --profile headless "任务"` 跑完即退），**不是 ACP profile**；能挂 ACP 的是
`acp` / `ssot-agent` 这类。所以：

- 固定开销要对比，得换**另一个能挂 ACP 的 profile**（例如 `acp`），或者直接从 harness 的
  配置里数工具定义——**这轮没做**，`OPEN.md` #25 保留。
- ⚠️ 也说明 spike 那条 headless 路线与我们的生产路线**不是同一套东西**，
  它的 token 数字只能当**量级参考**，不能当基线。

|---|---|---|
| 实体来源行 | 92 | **1,199** |
| 去重后实体 | 89 | 695 |
| 关系行 | 65 | 1,217 |
| **Other 占比** | **26/92 = 28%** | **66/1,199 = 5.5%** |

类型分布（14 篇）：人物 290 / 式神 200 / 机制 188 / 地点 163 / 物品 152 / **Other 66** /
技能 58 / 组织 52 / 数值 30。

**读数**：把坏例写进提示词这一条**明显有效**——`Other` 从 28% 掉到 5.5%（5 倍）。
⚠️ 两个口子：① 两批文档构成不同（3 篇是 `docs/式神`+`docs/机制`，20 篇主要是 `raw/剧情`，
剧情体里人物/地点天然多），所以**别把它当严格的 A/B**；② 数字是**中途读数**（14/20 篇），

### ⚠️ 复查（17/20 篇时）：**Other 占比下降 ≠ 抽取变干净**

把「像文件名/命令的实体」单独查了一遍，坏例**没有消失，只是换了类型**：

| 被抽成实体的坏例 | 现在被标成 |
|---|---|
| `docs/式神/<名字>.md`、`raw/式神/<名字>.md`（**连占位符都照抄**） | 物品 |
| `tables/式神技能.csv`、`tables/式神索引.csv` | 物品 |
| `增益减益.csv`、`式神技能.csv`、`技能说明.csv` | Other |
| `ssot vault`、`ssot vault query`（命令示例） | Other |

所以上面那张表**不能读成「提示词让抽取变干净了」**：`Other` 从 28% 降到 5.6%（76/1,358）
里，有相当一部分是**从 Other 挪进了具体类型**（比如文件路径被标成「物品」）——
那比留在 Other 更糟，因为它看起来像正常数据。

**结论（下一步要做的）**：提示词是「劝」，不是「拦」。要在**代码里**加**确定性过滤**：
名字里带 `.md` / `.csv` / 路径分隔符、`<...>` 这类占位、工具与命令名（`ssot …`、`dsh …`）
一律**丢掉并记原因**（进 `Dropped`），而不是继续往提示词里加字。
这条没做之前，**现在库里的图不能当图用**（`docs/式神/<名字>.md` 那种行必须清掉）。
### 20 篇跑批的结果：**33/37 批后被一个真 bug 打断**（2026-09-18）

计划 37 批（20 篇 / 每批 8 块）。**33 批完成并入库**（约 264 块），第 34 批挂了：

```
错误：第 34/37 批失败：第 1 轮回包解析失败：JSON 解析失败：
invalid character '{' after top-level value
```

**原因**：模型把答案拆成**两个 JSON 对象连着吐**（`{...}{...}`），而我的解析是
「取第一个 `{` 到最后一个 `}`」——中间夹着两个对象，自然解析不了。

**已修**（`ParseResponse` 改成扫**所有括号配平的对象**再合并，含转义与字符串内括号的处理；
测试里钉了「两个对象该合并」）。总耗时 **2,028.7 秒（约 34 分钟）**。

⚠️ **这批产物不能当成品**，两个原因：
1. **坏例还在**：跑批时过滤器（见下）还没落地，所以 `docs/式神/<名字>.md`、`tables/*.csv`、
   `ssot vault` 那些行**已经写进库了**；
2. 33/37 批 → 约 18 篇覆盖，不是 20 篇。

→ 结论：**要重建索引 + 重抽一遍**（派生层可重建，这是它的好处；钱是省不回来的）。

### 确定性过滤（这一轮落的代码，`vextract/filter.go`）

规则（宁少勿多，别误伤真实体名）：文件名后缀（`.md`/`.csv`/…）、路径分隔符、占位符（`<…>`/`{}`/`$`）、
命令与工具名片段（`ssot `/`dsh `/`mcp__`/`--patch`…）、空占位词（`无`/`待定`/`N/A`）、
**只有数字**（序号/年份）——命中就丢，并把人话原因写进 `Dropped`。

**一处自我纠正**：第一版把 `263%` 也拦了（当成「纯数字」）。但带单位的量是合法实体
（词表里就有「数值」），所以收窄成「**只拦纯数字**」——`2026`/`1.2` 丢，`263%` 留。
### 干净版 20 篇跑批：37/37 批跑完（2026-09-18）

重建索引（清掉脏图）后，用**带确定性过滤器 + 解析修复**的版本重抽 20 篇：

| 项 | 实测 |
|---|---|

| 抽取产出 | **1,312 实体 / 1,318 关系 / 3 丢弃** |

**读数（按字面读，别加戏）**：
