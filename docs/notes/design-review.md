# 设计复查：从原始诉求出发

> 目的：抛开既有路径，回到诉求本身，检查 984 行规格是否真的对准了要解决的问题。
> 本文是**自我批评**，不是总结。找的是站不住的地方，不是做得好的地方。

## 三、五个站不住的地方

### 1（最严重）：核心诉求是"计算"，而计算是空白

你的原话：

> 阴阳师最重要的游戏机制是 pve 的伤害计算和速刷还有 pvp 的斗技，都需要**算伤害，速度，看御魂**

而实际发生的：

- 框架评估阶段我**发现**了 `text/template` 不能算术、离线无任何表达式库；
- 之后的五份规格里，我反复写「**不得使用任意表达式**」；
- 却**从未回答"那到底怎么算"**。

于是形成一个荒谬的结果：**我们建了一套精细的数据治理体系，来保证"数据不错"，但整个系统算不出一个伤害数字。**

而"不能错"的最后一环恰恰是**算对**。数据再准，公式算错，结果就是错的。

**这不是遗漏，是方向偏离。**

### 2：周期性 / 时间线完全没有建模

案例 1（每月攒勾玉/蓝票/黑蛋）的核心是**周期性**：每日任务、每周副本、每月活动、限时双倍。

我们的限定条件里有「版本 / 时间区间 / 场景 / 触发条件」，但**没有"每周期重复"**这个语义。
「每个月能攒多少」在当前模型里表达不出来。

案例 2 需要排期（距活动开始还剩多久、来不来得及），同样没有时间线模型。

### 3：文档的角色没定义

R3 明确要求管「文档」。我们的处理是：

- 定义了 `longtext` 类型
- 实测了中文检索（LIKE vs FTS5）
- 结论是"用 LIKE"

但**没有回答**：文档是**依据**（溯源锚点指向它）还是**内容**（用户要读的东西）？它如何参与方案？它本身要不要被校验？

我的判断是：**在这个系统里，wiki 原文的角色是「依据」**——429 个页面是断言的证据来源，不是产品内容。
这个定位必须**写下来**，否则实现时会走偏（比如去做一个 wiki 阅读器）。

### 4：核验层的精细度超过了执行能力

verification 有 107 行：四级方法、独立性判定、部分核验、抽检、重核验触发、人力排序。

但规模是：

- 275 个式神、上千个技能、1126 条 buff 条目
- **执行者可能只有你一个人**

一个人不可能核验完。**设计得再精细，没有执行者就是空的。**

我们确实写了"未核验允许使用但必须可见"，所以不会阻塞。但需要更明确的定位：
**默认全部不可信，按需核验，其余靠自动检查与社区共识。** 而不是设计一套假设有专职审核团队的流程。

### 5：大量能力与 wiki 自身重复

wiki **已经提供**：

| wiki 已有 | 我们重复造的部分 |
|---|---|
| 修订历史（`revid` + `parentid` + 时间戳） | provenance 的很大一块 |
| schema（`Data:Character.schema`，含类型与枚举） | 元模型的形状 |
| 多人编辑与回退 | 某种形式的人工审核 |

**我们的真实增量在 wiki 没有的地方**：

- 跨源交叉验证（灰机 vs biligame vs 社区）
- 断言分级（官方文案 vs 玩家补全，wiki 里是混在一起的）
- 系统化的冲突呈现（wiki 上两个页面矛盾，没人会系统性发现）
- **面向求解的投影**（伤害、配速、御魂）
- 与个人状态结合

重心应该压在**这些**上，而不是重新实现一套存储与版本管理。

## 四、两个真空白（必须补）

| 空白 | 影响 |
|---|---|
| **计算与公式**：怎么表达、怎么执行、怎么验证正确性 | 直接决定 R1/R4/R5 成立与否 |
| **时间与周期**：周期性产出、排期、时间线 | 直接决定 R5 的案例 1 与案例 2 |

## 五、复杂度是否超配

对比两条路：

**A（当前设计）**：断言模型 + 元模型 + 接入/准入 + 迁移 + 核验 + 方案 + 档案 ＝ 984 行规格，0 行实现

**B（极简）**：wiki JSON + 校验脚本 + Go 计算库 + 本地状态文件，用 git 管版本

B 能覆盖什么：

| 诉求 | B 能否覆盖 |
|---|---|
| 不能错 | ✅ 校验脚本 + 测试用例 |
| 跨源验证 | ✅ 脚本 |
| 溯源 | ✅ JSON 里记 revid |
| L1–L4 分级 | ✅ 就是一个字段 |
| 核验 | ✅ 一个 status 字段 + 审核界面 |
| 计算 | ✅ Go 代码（本来就要写） |
| 多解方案 | ✅ Go + 模板 |
| 迁移 | ✅ git diff + 迁移脚本 |

**A 的额外价值**在于：结构化的约束/冲突/时效管理，支撑**规模化与多写入方**。
**B 的优势**在于：单人单机、这个数据量级下，能**快得多**地跑出结果。

你的写入方是 agent / 脚本 / 外部同步（**多写入方**），所以准入与变更集**确实有价值**。
但现在的规模（423 页 / 275 式神）**还不需要**这层复杂度来兑现价值。

**结论不是推翻 A，而是：A 的价值要在规模出现后才兑现，现在应该先用最小可行路径跑通一个案例，再按需增厚。**

## 六、建议的调整

1. **立刻补「计算与周期」规格**——这是核心诉求，且是真空白。优先于任何实现。
2. **砍一个垂直切片先端到端跑通**，而不是全量实现。
   建议切片：**一个式神的属性 → 一次伤害计算 → 一个"我的式神够不够"的对比**。
   这条链同时穿过：接入 → 准入 → 断言 → 校验 → 计算 → 方案 → 个人状态。跑通了，架构就成立了；跑不通，问题会立刻暴露。
3. **核验层重新定位**为「标记为主、按需核验」，与单人执行能力匹配。
4. **写明文档的角色**：是依据，不是内容。
5. **列出"复用 wiki 已有能力"清单**，避免重复造。

## 七、如果重来，我会这样排序

```
1. 打通最短链路：一个页面 → 抽一条数据 → 校验 → 存 → 算一个数 → 输出
2. 补计算与周期（真空白，且是核心）
3. 扩数据面（经济/活动/版本）
4. 按需增厚治理层（迁移、核验精细化）
```

而不是：

```
1. 写 984 行规格（已完成）
2. …
```

**规格本身是资产，不是浪费**——它们把边界想清楚了。但**顺序错了**：
在验证最短链路能跑通之前，就先把治理层设计到了 984 行，
其中相当一部分能力（迁移引擎、核验流程）要等到规模出现才用得上。

## 八、一个需要你回答的问题

这套东西的**规模预期**是什么？

- 如果就是**你自己用**、数据量在千级、写入方其实主要是你手工触发的同步脚本：
  **B 路线的复杂度更匹配**，A 的很多层可以后置。
- 如果目标是**做成一个可给别人用的工具**、多写入方并发、长期维护：
  **A 的准入与变更集是必要的**，但也要接受"先跑通再增厚"。

这个答案会决定：下一步是做**计算与周期规格**，还是先**砍到最小可行路径**。
