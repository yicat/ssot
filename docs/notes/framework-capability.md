# 框架能力评估（对照需求的实测结论）

> 方法：对每个存疑点做一次性实验，能用真实数据就用真实数据（423 个 wiki 页面 / 10 MB），
> **不靠推理**。实验代码在 `spike/`，已删除；结论在此固化。
> 环境：Go 1.26.5 / Wails v3.0.0-beta.16 / modernc.org/sqlite v1.58.0（SQLite 3.53.4）

## 一、结论速览

| # | 你的要求 | 判定 | 依据 |
|---|---|---|---|
| R1 | 提供数据库 | ✅ 满足 | 纯 Go SQLite，无 cgo，离线可用，WAL |
| R2 | 提供 schema（元模型代码 + schema 文件） | ✅ 满足 | JSON 列可建索引、可加 CHECK，动态字段不必牺牲约束 |
| R3 | 提供校验方案 | ✅ 满足 | 六类约束中五类由数据库原生保证，实测全部生效 |
| R4 | 提供流程 | ⚠️ **部分** | 状态机可行；**schema 演进/迁移机制未验证** |
| R5 | 管数据 / 表 / 文档 | ⚠️ **有条件** | 数据表可行；**中文全文检索有真实约束** |
| R6 | 生成不同角度的方案 / 报告 | ❌ **不满足** | **标准库无表达式求值**，计算类视角无法配置化 |
| R7 | agent / 脚本 / 外部同步写入 | ✅ 满足 | server 模式实测：无 GUI 的 HTTP 二进制，`127.0.0.1:8080` 返回 200 |

**一句话**：数据、校验、外部接口这三块框架够用；**"不同角度的方案"这块框架不够**，需要补一层。

## 二、已验证的能力

### 2.1 SQLite：约束强度（R1 / R2 / R3）

```
journal_mode = wal
DDL（CHECK / UNIQUE / FK / JSON 列）  : OK
UNIQUE 冲突被拒                        : true
CHECK 约束被拒                         : true
外键被拒                               : true
并发写 20 次（同进程 20 goroutine）    : 成功 20 / 失败 0
并发后重复 name 组数（应为 0）         : 0
回滚后残留记录（应为 0）               : 0
```

多进程并发写（模拟 GUI + 同步脚本 + agent 三方同时写）：

```
worker gui  : 成功 300  失败 0  耗时 14ms
worker sync : 成功 300  失败 0  耗时 15ms
worker agent: 成功 300  失败 0  耗时 13ms
库内总记录 900   重复 (writer,seq) 组 0
```

→ `WAL` + `busy_timeout` 下多进程写可用，且唯一性由数据库守住，不靠应用层"先查再插"。

### 2.2 动态 schema 可以落成真约束，不必退化成裸 JSON（R2）

```
json_extract 取字段            : OK
在 JSON 字段上建索引           : OK
对 JSON 字段加 CHECK           : OK
json_each 枚举字段名与类型     : [atk:integer spd:integer]
```

**`json_each` 直接支撑"数据超出 schema"的检测**——与 `tools/wiki/verify.mjs` 里发现
`tags`/`Voice` 未被声明是同一件事，可以下沉到数据库层做。

### 2.3 外部接口（R7）

```
wails3 task build:server → bin/ssot-server.exe  (10.71 MB，无 GUI 依赖)
运行时：TCP 127.0.0.1:8080 LISTENING
HTTP GET / → 200，475 字节
```

→ 外部程序与 agent 通过 HTTP 访问是可行的。

## 三、发现的三个真实约束

### 约束 1（最严重）：表达式求值缺失 → 计算方法必须是代码

```
模板内直接写乘法 : template: t:1: unexpected "*" in operand
内置 add 函数    : template: t:1: function "add" not defined
注册 mul 后      : 基础攻击 3082 × 暴伤 1.2 = 3698.3999999999996   ← 只有这一条路
条件与循环       : 可用
```

标准库 `text/template` **只有比较、没有算术**。且离线缓存中**没有任何表达式库**：

```
github.com/expr-lang/expr        False
github.com/antonmedv/expr        False
github.com/Knetic/govaluate      False
github.com/google/cel-go         False
github.com/PaesslerAG/gval       False
```

**影响**：先前"视角定义写文件、新增角度不改代码"的说法，**对计算类视角不成立**。

视角必须拆成两层：

| 视角的组成 | 能否声明式 | 归处 |
|---|---|---|
| 选哪些记录、筛选 / 分组 / 关联 / 排序 | ✅ 可以 | YAML 视角文件 |
| 渲染布局 | ✅ 可以 | `text/template` |
| **伤害公式、配速、期望值等计算** | ❌ **不行** | **Go 代码（domain 层）** |

三条出路：

- **(a) 计算写成 domain 的 Go 函数，视角文件只引用函数名** —— 简单、类型安全、可测试；代价是新增公式要改代码
- **(b) 手写表达式求值器**（Pratt parser，约 200–400 行，纯标准库）—— 一次性成本换回配置化
- **(c) 联网后引入 `expr-lang/expr`** —— 当前不可用

> 建议：先走 (a)。因为伤害公式本身**还需要验证正确性**（社区口径不统一），
> 用 Go 函数写便于写单元测试；等公式稳定、且确实需要用户自定义时，再上 (b)。

### 约束 2：中文全文检索半残

真实数据实测（423 页 / 10,075,930 字符）：

| 查询 | LIKE 全表扫描 | FTS5 trigram |
|---|---|---|
| 伤害（2 字） | ✅ 357 条 / **18.7 ms** | ❌ **0 条** |
| 暴击（2 字） | ✅ 126 条 / 27.3 ms | ❌ 0 条 |
| 速度（2 字） | ✅ 128 条 / 19.8 ms | ❌ 0 条 |
| 御魂（2 字） | ✅ 126 条 / 23.5 ms | ❌ 0 条 |
| 抵抗（2 字） | ✅ 119 条 / 22.6 ms | ❌ 0 条 |
| 无视防御（4 字） | ✅ 16 条 / 25.9 ms | ✅ 16 条 / **540 µs** |

- 默认 `unicode61`：连续中文被当作**一个 token**，只有整块命中才算（「防御」能中，「伤害」不能）
- `trigram`：**查询词 < 3 字符即失效**——而中文高频词恰恰多是 2 字（伤害/暴击/速度/御魂/抵抗）
- `LIKE '%词%'`：全表扫描 18–27 ms，**正确且够用**

**结论：这个规模（≤ 万级文档）用 LIKE，不要用 FTS5。**
语料再大一个数量级，才值得自建 bigram 索引或引入中文分词。

### 约束 3：server 模式无认证

`ssot-server.exe` 监听 `127.0.0.1:8080` 且**不鉴权**——本机任何进程都能读写。

对"agent / 脚本写入"是便利，但也意味着：
- **不能把端口暴露到局域网**
- 需要评估"本机不可信进程"这一威胁（任何程序都能改你的唯一事实源）

## 四、未验证 / 待确认

| 项 | 为什么重要 |
|---|---|
| **schema 演进与迁移** | 你列的三大流程之一，但"schema v1 → v2 时既有数据怎么办"目前**完全没有机制** |
| **文档的存储形态** | 存进 SQLite，还是保留原始文件 + 只存元数据？检索能力与溯源能力不同 |
| **server 模式下绑定服务能否被外部调用** | 本次只验证了静态前端返回 200，**没有验证 Go service 暴露成 HTTP 接口** |
| 高并发写入 | 只测到 900 条；批量导入十万级的锁竞争未测 |
| 循环引用 | 引用完整性的边界未定 |

## 五、对设计的影响

1. **收回"视角完全声明式"**。计算类视角必须有 Go 代码支撑；选择类视角才能纯配置。
2. **文档检索用 LIKE**，不引入 FTS5，避免中文 2 字词失效的坑。
3. **JSON 列 + 表达式索引 + CHECK** 让动态 schema 不牺牲约束强度；`json_each` 天然支持漂移检测。
4. **让应用成为唯一写者**：多进程直连虽实测可用，但把外部写入统一收敛到 server 模式的 HTTP 接口，
   可一并解决并发、鉴权与审计三件事。
5. **R4（流程）是当前最大的机制空白**，应当优先于"报告生成"去设计。
