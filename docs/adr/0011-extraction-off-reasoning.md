# 0011 抽取任务：关推理 + 受限工具集 + 批量调用

状态：已定（有实测数据）
关联：`docs/specs/derived.spec.md` §九.3、`docs/notes/extraction-spike.md`、`.dsh/extraction.patch.yml`

## 背景

派生层要抽实体/关系（LightRAG 机制）。抽取是**一次次模型调用**，成本与耗时取决于三件事：
推理开不开、工具集多大、一次调用塞多少内容。这三件都没量过之前，整库抽取的成本是未知数。

## 决策

抽取类任务一律：

1. **关推理**：`reasoningEffort: off`（DeepSeek 适配器只认 `{off,low,high,max}`，`off` 落成
   wire 上的 `thinking: disabled`）；
2. **受限工具集**：`ssot-agent` 同款禁用清单（pwsh/bash/fs/str-replace-editor），
   既省「工具定义」体积，又强制它走能力层；
3. **批量调用**：多块/多篇合进一次调用——**绝不允许「一块一次调用」**。

## 为什么（同任务三跑，3 篇文档）

| | 输入合计 | 输出 | 耗时 | 工具定义 token |
|---|---|---|---|---|
| run1 默认（推理开 + 全套工具） | 54,657 | 13,327 | 75.0 s | 7,863 |
| run2 关推理 | 28,898 | 11,975 | 43.9 s | 7,863 |
| **run3 关推理 + 收工具集** | **23,298** | **6,577** | **25.8 s** | **5,220** |

run1→run3：**输入 −57%、输出 −51%、耗时 −66%**，格式与行号质量不变（坏行号 0）。

**为什么「批量」是硬约束**：单次调用的固定开销 ~21.5k token（system + 工具定义 + 消息）。
8,667 块逐块抽 ≈ 8667 × 21.5k ≈ **1.9 亿输入 token**，纯浪费。

## 否掉的选项

- **开着推理抽**：输入翻倍（推理文本会进对话历史，之后每次调用重发一遍）。
- **用 dsh-base 全套工具抽**：每次多花几千 token 的工具定义，还多一条绕过能力层的路。
- **逐块抽（LightRAG 的朴素做法）**：成本量级不可接受。
- **更小的模型/自己写 LLM 客户端**：会多一套凭据与重试管理；先用现成后端（可替换，见 0005）。

## 后果

- 校准后的外推：每篇 ≈ 7.8k 输入 / 2.2k 输出 → demo 410 篇 ≈ **3.2M 输入 / 0.9M 输出**、
  单机单线程 ≈ **59 分钟**（可并行压时间，不压 token）。
- ⚠️ 未证实：关掉后仍出现 2 段 `dsh: reasoning`，所以「thinking 是否真被禁用」要看 wire 层；
  且**质量只验到「格式没坏」**（见 `docs/OPEN.md`）。
