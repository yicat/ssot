# 0007 派生层沉到水下，用户只见文档与数据表

状态：已定
关联：`docs/specs/derived.spec.md`、`docs/specs/vault.spec.md` §4、`docs/plans/derived-layer.md`

## 背景

LightRAG 那套（KV / 向量 / 图 / 文档状态四种存储 + 实体关系抽取 + 混合检索）确实有用，
但它的产品形态是「喂给 LLM 的检索片段」；我们的产品形态是「**文档 + 数据表**」，
人要能读、能引用、能自己判断。

## 决策

- **用户可见的只有** `docs/`（整理层）、`raw/`（原始层）、`tables/`（数据表）；
- 底下的 KV、实体关系图、向量**全部是派生物**：落在 `.data/index.db`，**可重建、不进 git、不进人眼**；
- 抽取/嵌入/图维护**自动进行**，人不需要（也不应该）手工维护索引。

## 为什么

- 「事实只存在文件里」这条一旦破（比如把抽取结果也当事实存起来），删掉索引就会丢内容，
  而且会出现「文件里没有、但系统里有」的第二种真相。
- 用户要的是「查得到、看得到出处」，不是「维护一个知识图谱」。

## 否掉的选项

- **把抽取产物写进 `docs/`**：会让重建变成不可能（丢内容），也让 git 里塞满机器生成物。
- **让用户手工维护实体/关系**：那是把内部实现当产品；而且人维护不动。
- **引外部向量库/图库服务**（Milvus、Neo4j…）：多一个要起、要备份、要管生命周期的东西，
  我们的规模（几千到几万条）不需要。

## 后果

- 派生层必须能**整层删掉重建**，且删除不损失任何内容（`docs/specs/derived.spec.md` §五）。
- 人做的**纠正**是例外，必须落在文件里（0009），否则重建就丢。
- 检索结果必须能回指到「哪篇文档的哪一行」，回指不到的一律不允许存在。
