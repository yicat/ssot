# 0012 不做问答/RAG 生成链

状态：已定
关联：`docs/specs/agent.spec.md` 定位、`docs/specs/vault.spec.md` 定位/不做、`docs/notes/oss-comparison.md` §五

## 背景

对标的三个开源项目（WeKnora / MaxKB / LightRAG）都是「检索 → 生成答案」的形态：
用户问一句，系统回一段自然语言。我们借了 LightRAG 的**存储与检索机制**（见 0007、0010），
于是必须明确回答：**要不要连生成链一起做**。

## 决策

**不做**。检索结果给**人或 agent** 看：人看文档与命中位置，agent 通过工具拿到片段后自己读文档。
系统不生成「答案」。

## 为什么

- 我们的产物是**文档**（可引用、可编辑、有出处），不是一次性回答；生成链会把「哪句话有出处」
  这件事糊掉（MaxKB 的反面教训：LLM 答案直接落库、与原文同权）。
- 生成链一旦存在，就必须回答「这个答案是核验过的吗」——而我们的答案是「只有人能发布」，
  两者在界面上会打架。
- agent 场景下，我们已经有更好的形态：**工具 + 文档**。让模型自己读、自己引，比让它读一段
  二手总结更可靠。

## 否掉的选项

- **内建问答框**（WeKnora/MaxKB 形态）：与「未核验可见」「发布必须是人」冲突。
- **把检索片段拼成 prompt 自动总结**：等价于做了一条隐形的生成链，出处会被稀释。
- **只做「总结选中段落」这类轻量生成**：看着无害，但它同样产出**没有出处的文本**；
  真要做就应该是「写进文档、标 draft、留 trailer」，即走正常写入路径（0002/0003）。

## 后果

- 界面上不出现「问答」入口；agent 的能力体现为**工具调用与引用**（工具调用行单独显示，
  见 `docs/specs/document.spec.md`）。
- 「核验」这件事由人 + agent 的分工承担（`agent.spec.md` 的四个角色），不靠生成链兜底。
