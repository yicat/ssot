# 0008 嵌入走 B（512 块 + bge-small-zh），C 被实测否掉

状态：已定（有实测数据）
关联：`docs/specs/derived.spec.md` §九.1、`docs/notes/embedding-spike.md` §六

## 背景

要选**嵌入模型**与**块大小**。两套候选：

- **B**：512 token 子块 + `bge-small-zh-v1.5` int8（22.9MB、512 维）；
- **C**：2000 token 块 + `bge-m3`（542MB、1024 维、8192 上限，LightRAG 那类默认搭配）。

## 决策

**B**（嵌入）。同时：**抽取用 2000 token 块**（LightRAG 的 `DEFAULT_CHUNK_P_SIZE`），
即「抽取块与嵌入块解耦」。

## 为什么（都是量出来的，不是感觉）

召回实验（200 篇 / 302 条查询，同一批文档与查询）：B R@1 65.9% / R@5 77.8%，
C R@1 69.2% / R@5 78.1%；配对比较 R@1「只有 B 对 33 / 只有 C 对 43」→ **McNemar p≈0.30 不显著**，
R@5 **完全打平**（27 vs 28）。分长度看：head/mid C 好（+14pp/+8pp），**tail B 反而好 12pp**
（2000 的块把尾部内容稀释了，命中块也是 B 更细：201 vs 345 字符）。

成本：C 的模型 **542MB vs 22.9MB**、加载 30.2s vs 3.9s、RSS +910MB vs +80MB、
2000-token 块单条 481.9ms vs 12.7ms，**全库重建 60 分钟 vs 79 秒**。

**结论：C 的优势没有证据，代价是 18–45 倍。**

## 否掉的选项

- **C（大模型 + 大块嵌入）**：见上。留作可选升级项，不做默认。
- **A（2000 块 + 512 模型）**：31.9% 的块超过 512 token，**超过一半字符进不了向量**——
  那不是精度问题，是丢内容。直接排除。
- **按 2000 块截断后嵌入**：等于 A。

## 后果

- 分发体积保持 39MB（模型 22.9 + ORT 15.7），不必走「首次运行下载 542MB」。
- 检索的命中粒度更细（对我们的「哪一段说了」更有利）。
- ⚠️ 未测：**抽取质量**（512 上下文会不会把实体/关系抽碎）——那要真调 LLM，
  见 `docs/OPEN.md`。
