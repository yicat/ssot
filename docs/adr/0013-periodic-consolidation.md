# 0013 定期整理：触发式为主 + 台账

状态：**提议（待确认）**——这条是我按用户的提问提的方案，用户还没拍板；先记下来免得又散掉。
关联：`docs/STATUS.md`（台账）、`docs/OPEN.md`（巡检项）、`docs/specs/vault.spec.md` 未定 #2、`docs/specs/derived.spec.md` §六.1

## 背景

用户问：「有定期整理的方案和记录吗？」核对结果：**两层都没有**。

- 我们自己的文档治理：只有被动机制（spec 的「未定」小节、notes、git 历史），
  没有 cadence，也没有「上次整理于何时、做了什么」的台账；
- 产品层面的 vault 内容：「整理」有角色（`raw/` → `docs/`），但没有「多久一次、谁触发、
  记录放哪」；而且它正好卡在三个未定项上（索引何时重建、抽取何时触发、整理动作本身的记录）。
- 对照教训（我们自己记过）：WeKnora 的 `stale_ref` lint **没有定时任务**，只在按需调用时检测。

## 提议

**触发式为主，日历式为辅**，不搞「每周必须整理」这种空转：

1. 触发条件：① 每个 P 阶段收尾；② 有决策被修订时（新开 ADR + 在旧 ADR 顶部写「被 NNNN 修订」）；
   ③ 固定巡检（每 20 次提交或每周一次）扫 `OPEN.md` 的过期项与 spec 的「未定」。
2. 台账：`docs/STATUS.md` 顶部固定一行 `上次整理：YYYY-MM-DD（做了什么）`，
   每次整理追加一行表（日期 / 范围 / 结论 / 关联 ADR）。
3. 产品侧：定期动作落到 `derived.spec` 的触发方式上（倾向「写入即排队 + 空闲批量」），
   再加一个**可选**的每日巡检（断链 / 孤儿页 / 引用失效 / 索引过期）；
   巡检结果要落在**文件**里（`.data/` 会随重建丢），具体放 `docs/` 还是 table 待定。

## 为什么（不是洁癖，有两次实证）

- `docs/notes/oss-comparison.md` 写着「借机制 → 落进 spec」，实际**一条都没落**，
  直到几个月后核对才发现（那次已补落位表）；
- 「冲突并列不裁决」（0004）**被 0009 静默修订**过，修订这件事没有独立记录，
  只能从对话里追溯——**这正是 ADR + 台账存在的理由**。

## 否掉的选项

- **纯日历式（每周/每天必须整理）**：没有新决策可整理时就是空转，很快会被无视。
- **不记录、只靠 git 历史**：git 记的是「改了什么」，不记「为什么改、当时否掉了什么」——
  0004 被修订这件事 git 里看不出来。
- **把整理记录写进 `.data/`**：重建即丢（0011/0007 的同类理由）。

## 后果（若采纳）

- 需要维护 `STATUS.md` 的台账与 `OPEN.md` 的状态流转（谁改状态、什么时候）。
- 定期动作会产生**额度的持续消耗**（抽取/巡检），要给人一个开关与可见的进度。
