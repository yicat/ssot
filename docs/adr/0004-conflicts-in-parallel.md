# 0004 冲突并列、系统不裁决

状态：**被 [0009](0009-llm-summary-plus-human-correction.md) 修订**（派生层的图描述改为「LLM 合成 + 人机纠错优先」；文件层的并列立场不变）
关联：`docs/specs/vault.spec.md` §6、`docs/notes/oss-comparison.md` §三/§五

## 背景

两份文档、两个来源对同一件事说法不同的时候怎么办。这是这类工具最核心的分歧点：

- LightRAG：把同名实体的描述列表交给 LLM 总结成一段话（`prompt.py:297-328`）；
- MaxKB：LLM 的答案直接落成新段落并进库（`application_chat_record.py:368-375`）。

## 决策

**并列 + 双链相连，系统不裁决**：冲突的两边都留着，各自带来源；系统不选一个，
也不把两个说法合写成一句。

## 为什么

LLM 合并**不可复现、不留痕**：同一次输入换个模型或换个温度就可能得出不同结论，
而「谁赢了」这件事本身没有记录。我们要的是「看得出来有两种说法，各自出自哪里」，
判断权交给人。

## 否掉的选项

- **LLM 合并成一段**（LightRAG 做法）：看着整洁，但裁决者变成了模型。
- **按时间/版本自动选新的**：新旧不等于对错，且会静默丢掉旧说法。
- **只显示一条、另一条折叠**：等于变相裁决（谁被折叠谁就消失了）。

## 后果

- 检索与界面上要能同时呈现两个来源（这是显示层的负担，接受）。
- 派生层的实体描述因此曾定为「不合并」；**后来按用户拍板改成了「合成 + 纠错优先」**（0009），
  但**文件层仍然并列**——文档里的两种说法一个字都不会被改掉。
