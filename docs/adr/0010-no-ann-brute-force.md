# 0010 向量不上 ANN：暴力扫 + 确定性

状态：已定（有实测数据）
关联：`docs/specs/derived.spec.md` §三、`docs/specs/vault.spec.md` §搜索（`RankHits`）

## 背景

向量检索要选索引方式：ANN（HNSW/IVF 之类）还是**暴力扫全量**。
直觉上「几万条向量必须上 ANN」，但我们没有量过。

## 决策

**暴力扫**：向量存 SQLite 的 BLOB（float32），相似度在进程内算（归一化后点积即余弦）。
**不上 ANN**、不引 `sqlite-vec` 加载扩展、不引外部向量库服务。

## 为什么（实测，512 维、`CGO_ENABLED=0`、50 次查询取平均）

| 规模 | 内存 | 每次查询 |
|---|---|---|
| 1,000 条 | 2.0 MB | 0.23 ms |
| 10,000 条 | 19.5 MB | 1.99 ms |
| 100,000 条 | 195.3 MB | 20.15 ms |

本项目的量（demo 407 篇 ≈ 4–8 千条块向量）落在 **~2 ms** 那一档。
更关键的是：**ANN 是近似索引，会破坏「同一份 vault 同一次查询，结果顺序永远一样」**
（`vault.spec.md` 的确定性要求）；暴力扫天然确定。

## 否掉的选项

- **ANN（HNSW/faiss 之类）**：多一层近似、少一分可复现，换来的延迟收益在本项目的规模下不存在。
- **`sqlite-vec` 扩展**：要加载扩展（多一个二进制产物与平台适配），收益与上一条相同。
- **外部向量库服务**：见 0007 的同类理由（多一个要起、要备份的东西）。

## 后果

- 到 **~10 万条**（≈1 万篇文档）再动手，顺序写清楚了：
  ① 先用 FTS / 图邻居把候选缩小；② 向量量化成 int8；③ 那时才谈 ANN。
- 检索的融合权重必须写死 + 稳定排序（不许有随机），否则确定性还是破。
