# Spec 先行（SDD）

## 何时必须写 spec

- 新增特性
- 修改既有对外行为（API、wails3 bindings、用户可见流程）
- 改动前后端契约
- 缺陷修复若需要明确边界（复现条件、期望行为）

纯重构、格式化、依赖升级不需要 spec。

## 模板

写入 `docs/specs/<feature>.spec.md`：

```markdown
# <特性名>

## 目的
<解决什么问题，为谁解决>

## 领域规则（Given-When-Then）
- Given <前提> When <动作> Then <结果>

## 验收标准
- [ ] <可观测、可测试的结论>

## 边界与异常
- <输入为空/超限/并发/失败时的期望行为>

## 前后端契约
- <方法名、参数、返回字段与类型、可空性>
```

## 流程

1. 写 spec 到 `docs/specs/<feature>.spec.md`
2. **验收测试（红）**：测试条目直接对应「验收标准」
3. **领域端口接口**：在 `internal/domain/<area>/` 定义接口，不写实现
4. **实现（绿）**：先 `application` 编排，再 `infrastructure` 适配
5. **重构**：只改实现，规格不动

## 检查项

- [ ] 每条验收标准都有对应测试
- [ ] 「边界与异常」每一项都有明确期望
- [ ] 前后端契约写清了字段、类型、可空性
- [ ] 规格与实现冲突时，先改规格再改代码

## 常见失败

- 测试数少于验收标准条目 → 漏测
- 规格里出现函数名、文件路径 → 越界，规格只描述行为
- 先写实现再补 spec → 失去"规格即事实源"的意义，返工时先补测试
